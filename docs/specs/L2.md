# L2 - Detailed Requirements

## Cooperative Management Platform

This document defines detailed requirements with acceptance criteria. Each requirement traces to a parent L1 high-level requirement.

---

## User Account Management (L1-REQ-001)

### L2-REQ-001: Create User Account

**Traces to:** L1-REQ-001

The system shall allow creation of a new user account with a username and password.

**Acceptance Criteria:**

- AC1: A user is created with a unique username and a securely hashed password.
- AC2: The password is stored as a salted hash using a cryptographically secure random 16-byte salt.
- AC3: The system returns the created user's identifier upon success.
- AC4: The system rejects creation if the username already exists.

---

### L2-REQ-002: Update User Account

**Traces to:** L1-REQ-001

The system shall allow updating an existing user's details.

**Acceptance Criteria:**

- AC1: An authorized user can update username and other account properties.
- AC2: The system returns the updated user record upon success.

---

### L2-REQ-003: Soft Delete User Account

**Traces to:** L1-REQ-001

The system shall support soft deletion of user accounts, preserving data for audit purposes.

**Acceptance Criteria:**

- AC1: Deleting a user sets the `IsDeleted` flag to true rather than physically removing the record.
- AC2: Soft-deleted users cannot authenticate.
- AC3: The system returns confirmation of deletion.

---

### L2-REQ-004: Change Password

**Traces to:** L1-REQ-001

The system shall allow users to change their own password by providing the current password.

**Acceptance Criteria:**

- AC1: The user must supply a valid current password to change their password.
- AC2: If the current password is incorrect, the request is rejected.
- AC3: The new password is stored with a new salted hash.

---

### L2-REQ-005: Admin Password Reset

**Traces to:** L1-REQ-001

The system shall allow administrators to reset a user's password without requiring the old password.

**Acceptance Criteria:**

- AC1: An administrator can set a new password for any user.
- AC2: The new password is stored with a new salted hash.

---

### L2-REQ-006: Check Username Availability

**Traces to:** L1-REQ-001

The system shall allow checking whether a username is already taken.

**Acceptance Criteria:**

- AC1: The endpoint is accessible without authentication.
- AC2: Returns a boolean indicating whether the username exists.

---

## Authentication and Authorization (L1-REQ-002)

### L2-REQ-007: User Authentication

**Traces to:** L1-REQ-002

The system shall authenticate users via username and password and return a JWT access token.

**Acceptance Criteria:**

- AC1: A POST request with valid username and password returns a JWT token and the user's identifier.
- AC2: The JWT token contains claims for UserId, Username, Roles, and Privileges.
- AC3: Invalid credentials return an appropriate error response.
- AC4: The authentication endpoint is accessible without prior authentication.

---

### L2-REQ-008: Resource-Based Authorization

**Traces to:** L1-REQ-002

The system shall enforce resource-level authorization on API endpoints using role privileges.

**Acceptance Criteria:**

- AC1: Each protected endpoint declares the required operation (Create, Read, Write, Delete) and target aggregate.
- AC2: A request from a user whose role lacks the required privilege is rejected with a 403 Forbidden response.
- AC3: Privileges are evaluated from the JWT claims at request time.

---

### L2-REQ-009: Current User Retrieval

**Traces to:** L1-REQ-002

The system shall allow authenticated users to retrieve their own account information.

**Acceptance Criteria:**

- AC1: An authenticated request to the current user endpoint returns the user's profile, roles, and active profile.
- AC2: Unauthenticated requests are rejected with 401 Unauthorized.

---

## Role and Privilege Management (L1-REQ-003)

### L2-REQ-010: Role CRUD Operations

**Traces to:** L1-REQ-003

The system shall support creating, reading, updating, and deleting roles.

**Acceptance Criteria:**

- AC1: A role can be created with a name.
- AC2: All roles can be listed.
- AC3: A role can be retrieved by its identifier.
- AC4: A role's name can be updated.
- AC5: A role can be deleted.

---

### L2-REQ-011: Privilege CRUD Operations

**Traces to:** L1-REQ-003

The system shall support creating, reading, updating, and deleting privileges associated with roles.

**Acceptance Criteria:**

- AC1: A privilege can be created specifying a role, an aggregate (resource name), and an access right (Read, Write, Create, Delete).
- AC2: Privileges can be listed, optionally filtered by aggregate.
- AC3: A privilege can be updated or deleted.

---

### L2-REQ-012: Predefined Roles

**Traces to:** L1-REQ-003

The system shall seed the following default roles on initial deployment: Member, Staff, BoardMember, SystemAdministrator, Support.

**Acceptance Criteria:**

- AC1: All five predefined roles exist after database seeding.
- AC2: Each predefined role has appropriate default privileges assigned.

---

### L2-REQ-013: Assign and Remove User Roles

**Traces to:** L1-REQ-003

The system shall allow assigning roles to and removing roles from users.

**Acceptance Criteria:**

- AC1: A role can be added to a user, granting the associated privileges.
- AC2: A role can be removed from a user, revoking the associated privileges.
- AC3: A user can hold multiple roles simultaneously.

### L2-REQ-091: Members Set Their Own Profile Picture

**Traces to:** L1-REQ-004, L1-REQ-008

The system shall let a member set, replace and remove the picture on their own profile, store it through the digital asset service, and show it beside the member's name on messages and on the maintenance requests the office reads. Only the profile's owner and the office may change it. Members do this on their admin profile (L2-REQ-108). The screens are drawn in `docs/mocks/pages/admin-member-profile/` (photo-preview, photo-saving, photo-saved, photo-invalid, photo-too-large, photo-error, photo-removed) and `docs/mocks/pages/admin-maintenance/detail-submitter-photo.html`. The design is `docs/detailed-designs/public-app/profile-picture/README.md`, moved to the admin site by `docs/detailed-designs/admin-app/member-areas-by-role/README.md`.

**Acceptance Criteria:**

- AC1: Given a signed-in member on their profile, when they choose a photo with "Choose a photo" (or "Choose another"), then the photo shows in the profile circle as a preview with "Save photo" and "Cancel", and nothing is saved yet.
- AC2: Given a previewed photo, when the member activates "Save photo", then the button reads "Saving…" and both buttons are disabled until the answer arrives; on success the picture stays in the circle, the page says "Your photo is saved.", and the picture is still there after the page is reloaded.
- AC3: Given a previewed photo, when the member activates "Cancel", then the circle shows the picture it showed before and nothing is saved.
- AC4: Given a chosen file that is not a JPEG, PNG or WebP picture, or is larger than 10 MB, when it is chosen, then it is not previewed and the page says "“{name}” is not a photo we can use. Choose a JPEG, PNG or WebP photo." or "“{name}” is too large. Choose a photo smaller than 10 MB." as an alert.
- AC5: Given saving fails, when the answer arrives, then the preview stays and the page says "Your photo was not saved. Please try again." as an alert.
- AC6: Given a member with a picture, when they activate "Remove photo", then the picture is removed, the circle shows the empty person mark, and the page says "Your photo is removed."; if removing fails, the picture stays and the page says "Your photo was not removed. Please try again." as an alert
- AC7: Given a member with a picture, when the office opens a request they made, then the picture shows beside "Submitted by"; without a picture the request shows nothing extra. (The picture beside a sender's messages was shown by the public messaging page, which is gone; showing it in the admin conversation is deferred, see `docs/detailed-designs/admin-app/member-areas-by-role/README.md`.)
- AC8: Given the API, when a picture is posted to `POST /api/profiles/{profileId}/avatar`, then it is stored as a digital asset and set as the profile's avatar only if the caller's user owns the profile or holds Write or higher on the `Member` aggregate; anyone else is refused with status 403. The same rule applies to `PUT /api/profiles/avatar` and to `DELETE /api/profiles/{profileId}/avatar`, which removes the picture.
- AC9: Given the API, when a picture is not `image/jpeg`, `image/png` or `image/webp`, or is empty or larger than 10 MB, then it is rejected with status 400 and the message "Choose a JPEG, PNG or WebP photo." or "Choose a photo smaller than 10 MB."
- AC10: Given a picture is replaced or removed, when the API answers, then the previous picture's digital asset is deleted and is no longer served.
- AC11: Given the same picture (same name, type and bytes) is posted again for the same profile, or a profile without a picture has its picture removed again, when the API answers, then it returns the profile unchanged (see `docs/adr/0006-idempotent-profile-picture-changes.md`).
- AC12: Given any viewport from 320 CSS px wide, when the profile picture controls render, then no horizontal scrolling is needed, every control is at least 44 px tall, and keyboard focus is visible.

### L2-REQ-092: Members Choose How They Get New Notices

**Traces to:** L1-REQ-004, L1-REQ-006

The system shall let a member choose on their own profile whether new notices the office sends reach them by email, by text message, by both or not at all, using the email address and phone number on that profile. Nobody gets notices until they choose to. Members choose on their admin profile (L2-REQ-108). The screens are drawn in `docs/mocks/pages/admin-member-profile/` (default, edit, notices-invalid, saved). The design is `docs/detailed-designs/admin-app/send-notices/README.md`.

**Acceptance Criteria:**

- AC1: Given a signed-in member on their profile, when the profile shows, then a "New notices" row says "By email", "By text message", "By email and text message" or "Not sent to you"; a member who has not chosen sees "Not sent to you".
- AC2: Given the member edits their profile, when the form shows, then a group named "Send me new notices" offers the checkboxes "By email" and "By text message", ticked as saved, with the hint "We use the email address and phone number above."
- AC3: Given the member ticks "By email" while the email field is empty, or "By text message" while the phone field is empty, when they activate "Save Changes", then nothing is saved and the group shows "Add your email address to get notices by email." or "Add your phone number to get notices by text message." as an alert.
- AC4: Given valid choices, when the member saves, then the page says "Your profile is saved.", the "New notices" row shows the choice and it is still there after the page is reloaded.
- AC5: Given the API, when `GET /api/user/profile` answers, then it carries `noticeByEmail` and `noticeByText`, both `false` until the member chooses; `PUT /api/user/profile` sets them on the caller's own profile only, and leaves either unchanged when it is left out.
- AC6: Given any viewport from 320 CSS px wide, when the choices render, then no horizontal scrolling is needed, each checkbox and its label is a target at least 44 px tall, and keyboard focus is visible.

## Maintenance Request Workflow (L1-REQ-005)

### L2-REQ-021: Create Maintenance Request

**Traces to:** L1-REQ-005

The system shall allow members to submit maintenance requests.

**Acceptance Criteria:**

- AC1: A maintenance request is created with the requesting profile's identifier, address, phone number, description, and unattended unit entry preference.
- AC2: The initial status is set to "New".
- AC3: The creation date is recorded.
- AC4: A domain event is published upon creation.
- AC5: The request records the requesting member's name from their profile, and the office sees it as "Submitted by".

---

### L2-REQ-022: Receive Maintenance Request

**Traces to:** L1-REQ-005

The system shall allow staff to receive (acknowledge) a maintenance request.

**Acceptance Criteria:**

- AC1: A request in "New" status can be transitioned to "Received".
- AC2: The receiving staff member's profile identifier and receipt date are recorded.
- AC3: A request not in "New" status cannot be received.

---

### L2-REQ-023: Start Maintenance Request

**Traces to:** L1-REQ-005

The system shall allow staff to mark a maintenance request as work started.

**Acceptance Criteria:**

- AC1: A request in "Received" status can be transitioned to "Started".
- AC2: The work start timestamp is recorded.
- AC3: Unit entry details are captured.
- AC4: A request in "New" status cannot be started; the API rejects the request with status 400 and the message "Only a received request can be started."
- AC5: Starting records a `Start` event, with the starting staff member's profile identifier, in the audit history (`StoredEvent`, aggregate `MaintenanceRequest`, stream the request identifier).
- AC6: Re-posting Start for a request that is already "Started" or "Completed" returns the request unchanged and records no second event (see `docs/adr/0004-idempotent-maintenance-request-steps.md`).

---

### L2-REQ-024: Complete Maintenance Request

**Traces to:** L1-REQ-005

The system shall allow staff to mark a maintenance request as completed.

**Acceptance Criteria:**

- AC1: A request in "Started" status can be transitioned to "Completed".
- AC2: The work completion date and completing staff member's name are recorded.
- AC3: A request in "New" or "Received" status cannot be completed; the API rejects the request with status 400 and the message "Only a started request can be finished."
- AC4: Completing records a `Complete` event, with the completing staff member's profile identifier, in the audit history.
- AC5: Re-posting Complete for a request that is already "Completed" returns the request unchanged and records no second event.

---

### L2-REQ-025: Maintenance Request Status Enforcement

**Traces to:** L1-REQ-005

The system shall enforce a strict forward-only status progression: New -> Received -> Started -> Completed.

**Acceptance Criteria:**

- AC1: Status can only transition in the defined forward order.
- AC2: Backward transitions or skipping statuses are rejected.

---

### L2-REQ-087: Office Steps on a Maintenance Request

**Traces to:** L1-REQ-005

The admin app's maintenance request detail, drawn in `docs/mocks/pages/admin-maintenance/detail-*.html`, shall offer the office the one next step of the lifecycle.

**Acceptance Criteria:**

- AC1: Given a "New" request, when the office opens it, then the detail offers "Receive Request" and no other lifecycle step.
- AC2: Given a "Received" request, when the office opens it, then the detail offers "Start work"; activating it starts the request (L2-REQ-023) and the status reads "Started".
- AC3: Given a "Started" request, when the office opens it, then the detail offers "Finish work"; activating it completes the request (L2-REQ-024) and the status reads "Completed".
- AC4: Given a "Completed" request, when the office opens it, then the detail offers no lifecycle step.
- AC5: Given the API refuses or fails a step, when the answer arrives, then the status is unchanged and the detail shows "That change was not saved. Please try again." as an alert.
- AC6: Given a step is being sent, when the button has been activated, then it is disabled until the API answers.

---

### L2-REQ-088: Member Sees Progress in Plain Words

**Traces to:** L1-REQ-005

The admin app's maintenance list and detail as a member sees them, drawn in `docs/mocks/pages/admin-member-maintenance/`, and the member dashboard's recent requests, drawn in `docs/mocks/pages/admin-member-dashboard/`, shall show the member each request's status in plain words. Members and the office use the same four words (design-system drift D28). Until 21 October 2026 the public app showed "Done" for a completed request; that screen is gone (L2-REQ-102).

**Acceptance Criteria:**

- AC1: Given a request the office has started, when the member views it, then its status reads "Started".
- AC2: Given a request the office has completed, when the member views it, then its status reads "Completed".
- AC3: Given a "New" or "Received" request, when the member views it, then its status reads "New" or "Received".
- AC4: Given the member's dashboard lists recent requests, when a request is shown there, then its status uses the same words as the Maintenance page.
- AC5: Given the Maintenance page, when the member filters it, then there is a filter for each status, "New", "Received", "Started" and "Completed", as well as "All".

### L2-REQ-089: Photos on Maintenance Requests

**Traces to:** L1-REQ-005, L1-REQ-008

The system shall let a member attach photos to their own maintenance request and let the office see them, keeping the photos private to the requesting household and the office. Members do this on the admin site (L2-REQ-107). The screens are drawn in `docs/mocks/dialogs/admin-member-maintenance-create/` (photos, busy, photo-invalid), `docs/mocks/pages/admin-member-maintenance/` (detail-photos, adding-photo, photo-error, photo-failed) and `docs/mocks/pages/admin-maintenance/detail-photos.html`.

**Acceptance Criteria:**

- AC1: Given a member creating a request, when they choose one or more photos, then each chosen photo is listed by name with a "Remove" action, and the hint "JPEG, PNG or WebP, up to 10 MB each." is shown under the labelled "Photos (optional)" picker.
- AC2: Given a chosen file that is not a JPEG, PNG or WebP picture, or is larger than 10 MB, when it is chosen, then it is not added and the form says "“{name}” is not a photo we can use. Choose a JPEG, PNG or WebP photo." or "“{name}” is too large. Choose a photo smaller than 10 MB." as an alert.
- AC3: Given a member sends a request with photos, when they activate "Send request", then the button reads "Sending…" and is disabled until the request and every photo are sent, and the request then shows the photos to the member and to the office.
- AC4: Given a photo fails to send after the request is created, when the answer arrives, then the form closes and the page says "Your request was sent, but a photo could not be added. Open the request to try again." as an alert.
- AC5: Given a member's existing request, when they choose "Add a photo" on its detail, then the photo is sent and shown; while it is sending the control reads "Adding photo…"; if it fails the detail says "The photo could not be added. Please try again." as an alert.
- AC6: Given the office opens a request, when it has photos, then the detail shows each photo with the text alternative "Photo {n} of {title}".
- AC7: Given the API, when a photo is posted to `POST /api/maintenance-requests/{id}/photos`, then it is stored through the digital asset service and attached to the request only if the caller's user owns the requesting profile; anyone else is refused with status 403.
- AC8: Given the API, when a photo is not `image/jpeg`, `image/png` or `image/webp`, or is empty or larger than 10 MB, then it is rejected with status 400 and the message "Choose a JPEG, PNG or WebP photo." or "Choose a photo smaller than 10 MB."
- AC9: Given the API, when a photo is read from `GET /api/maintenance-requests/{id}/photos/{photoId}`, then it is served to the requesting household and to roles holding Write or higher on the `MaintenanceRequest` aggregate; another member is refused with status 403 and an anonymous caller with 401.
- AC10: Given a maintenance request photo, when it is requested through the general asset routes (`api/digitalasset/serve/{id}` or by name), then it is not served.
- AC11: Given the same photo (same name, type and bytes) is posted again to the same request, when the API answers, then it returns the photo already attached and adds no second copy (see `docs/adr/0005-idempotent-maintenance-photo-upload.md`).
- AC12: Given any viewport from 320 CSS px wide, when the photo controls render, then no horizontal scrolling is needed, every control is at least 44 px tall, and keyboard focus on the picker is visible.

### L2-REQ-093: Office Sends a Published Notice to Members

**Traces to:** L1-REQ-006

The system shall let the office send a published notice once to every member who asked for new notices, by email to the address and by text message to the phone number on that member's profile. Sending goes through one sender service. When an SMTP server is configured, notice emails go out through it; text messages and any email sent while no SMTP server is configured are written to the API log and nothing leaves the system. The screens are drawn in `docs/mocks/dialogs/admin-document-create/` (send, busy, send-error) and `docs/mocks/notifications/admin-notice-sent/success.html`. The design is `docs/detailed-designs/admin-app/send-notices/README.md`.

**Acceptance Criteria:**

- AC1: Given the office in the "New Document" dialog, when the type is Notice and the status is Published, then an unticked checkbox "Also send to members by email and text" shows with the hint "Only members who asked for new notices on their profile get one."; for other types or the Draft status it does not show.
- AC2: Given the office saves a Notice with the status Published, when the save succeeds, then the notice is stored as a notice and published, so it shows under "What's on" on the home page and on the members' documents page.
- AC3: Given the box is ticked, when the office activates "Save", then the button reads "Saving…" and is disabled until the answer arrives; on success the dialog closes and the Documents page says "“{title}” is published and sent to members who asked for notices." as a status message.
- AC4: Given sending fails, when the answer arrives, then the dialog stays open with what was entered and says "“{title}” is published, but it was not sent to members. Press Save to try again." as an alert; pressing "Save" again sends it without creating a second notice.
- AC5: Given the API, when `POST /api/notice/{documentId}/send` is called, then each profile that chose "By email" and has an email address gets one email with the subject "New notice: {title}" and the notice text, and each profile that chose "By text message" and has a phone number gets one text message "New notice from the co-op: {title}. {text}"; profiles that did not choose, have no such address or are deleted get nothing, and an address shared by several profiles gets one message.
- AC6: Given a caller without Write or higher on the `Notice` aggregate, when they call the send route, then it is refused with status 403 and nothing is sent.
- AC7: Given a notice that is not published, or no notice with that id, when the send route is called, then it is rejected with status 400 and the message "Only a published notice can be sent."
- AC8: Given a notice that was already sent, when the send route is called again, then it returns the notice with the same `sentOn` and sends nothing (see `docs/adr/0007-send-a-notice-once.md`).
- AC9: Given an SMTP server is configured, when a notice is sent, then each chosen address gets one email from the configured sender address with the subject "New notice: {title}" and the notice text as a plain-text body.
- AC10: Given no SMTP server is configured, when a notice is sent, then each email is written to the API log and nothing leaves the system.
- AC11: Given the SMTP server refuses the message or cannot be reached, when a notice is sent, then the API answers with an error, `sentOn` stays empty, and a later send tries again (see `docs/adr/0008-send-notice-emails-over-smtp.md`).

### L2-REQ-080: Manage Website Pages

**Traces to:** L1-REQ-010

The admin app shall let an office administrator list, add, edit and remove the website pages that the public app shows (L2-REQ-083), from a "Pages" screen at `/pages` drawn in `docs/mocks/pages/admin-pages/` and its dialogs `docs/mocks/dialogs/admin-page-editor/` and `docs/mocks/dialogs/admin-page-remove/`.

**Acceptance Criteria:**

- AC1: Given a signed-in administrator, when the Pages screen loads, then it lists every page that has not been removed, oldest first, with its title and its public address `/pages/{slug}`, and offers "New page", "Edit" and "Remove" actions.
- AC2: Given no page exists, when the screen loads, then it shows the message "No pages yet" with a "New page" action instead of a list.
- AC3: Given the list cannot be loaded, when the screen loads, then it shows the message "We couldn't load the pages. Check your connection and try again." with a "Try again" action that reloads the list.
- AC4: Given the administrator activates "New page", when the editor dialog opens, then it asks for a page title (required), an optional hero photo chosen from the Assets library (L2-REQ-097 AC1) and shown as a thumbnail rather than an address, with its photo description (required when a photo is chosen, L2-REQ-097) and the page text (required, simple HTML), and focus moves into the dialog.
- AC5: Given the editor has an empty title or empty page text, when the administrator saves, then the dialog stays open, each missing field is marked invalid with the message "Give the page a title" or "Write something for the page", and nothing is sent to the API.
- AC6: Given a page already has the same title, when the administrator saves a new page with that title, then the dialog stays open and the title field reads "There is already a page called “{title}”. Choose a different title."
- AC7: Given valid fields, when the administrator saves, then the save button reads "Saving…" and is disabled until the API answers; on success the dialog closes, the list shows the page and the message "“{title}” is now on the website." is announced.
- AC8: Given the API rejects the save, when the answer arrives, then the dialog stays open with the entered values and shows the message "We couldn't save the page. Try again."
- AC9: Given an existing page, when the administrator activates "Edit", then the same dialog opens with the page's title, hero photo (with a "Remove photo" action), photo description and text filled in, and saving sends the changes with the page identifier.
- AC10: Given an existing page, when the administrator activates "Remove", then a confirmation dialog named "Remove “{title}”?" opens; "Remove page" removes it and the list no longer shows it, "Cancel" or Escape closes the dialog without change, and focus returns to the control that opened it.
- AC11: Given the API, when a page is created, then the page title shall yield a URL slug (lower case; letters and digits kept; other characters collapsed to single hyphens; accents removed; at most 80 characters); re-posting a page whose slug already exists returns the existing page unchanged instead of creating a second one (see `docs/adr/0002-idempotent-page-creation.md`).
- AC12: Given the API, when a page is updated so that its title would yield the slug of another page that has not been removed, then the update is rejected with status 400 and the message "A page with this title already exists."
- AC13: Given the API, when a page is created or updated with an empty title, a title with no letter or digit, a title longer than 120 characters, an empty body, a hero photo address longer than 2048 characters, a hero photo address without a photo description, or a photo description longer than 250 characters, then the request is rejected with status 400.
- AC14: Given any viewport from 320 CSS px wide, when the screen or a dialog renders, then no horizontal scrolling is needed, every control is at least 44 px tall, and the dialogs trap focus and make the page behind them inert.

### L2-REQ-081: Page Management Authorization

**Traces to:** L1-REQ-010

The API shall expose page management at `/api/pages` and restrict changes to roles that hold the matching privilege on the `Page` aggregate, enforced by the resource-operation authorization pipeline behavior.

**Acceptance Criteria:**

- AC1: Given an anonymous visitor, when they request `GET /api/pages` or `GET /api/pages/{slug}`, then the API answers 200 with the pages that have not been removed (404 when the slug matches none).
- AC2: Given a user whose roles hold the `Create` privilege on `Page`, when they `POST /api/pages`, then the page is created; `PUT /api/pages` requires `Write` and `DELETE /api/pages/{pageId}` requires `Delete` on `Page`.
- AC3: Given a signed-in member whose roles hold only `Read` on `Page`, when they `POST`, `PUT` or `DELETE` a page, then the API answers 403 and no page changes.
- AC4: Given an anonymous visitor, when they `POST`, `PUT` or `DELETE` a page, then the API answers 401.
- AC5: Given the seeded roles, when the database is seeded, then the SystemAdministrator role holds `Delete` on `Page`, and seeding adds the `Page` privilege to roles that predate it without duplicating existing privileges.

### L2-REQ-105: The API Refuses the Office Areas to Members

**Traces to:** L1-REQ-021

The rule is applied once, in the application layer's pipeline (ADR 0012), not per controller. **Acceptance Criteria:**

- AC1: Given a member's token, when it calls any of these, then the API answers 403 and changes nothing: users (`GET /api/user`, `/api/user/{id}`, `/api/user/page/…`, `POST`, `PUT` and `DELETE /api/user`, `PUT /api/user/password/reset`); roles (`/api/role…`); privileges (`/api/privilege…`); invitations (`/api/invitationtoken…` except `validate`); digital asset management (`/api/digitalasset` upload, avatar, by id, range, page and delete); profiles management (`DELETE /api/profiles/{id}`, `/api/members` list and by id, `/api/staffmembers…`, and creating or changing a board member); document changes and drafts (creating, changing, publishing, removing and sending documents, notices, bylaws and reports, and their full lists and pages); themes changes; JSON content changes, list and page; stored events (`/api/storedevent…`, `/api/events`); maintenance office work (`PUT /api/maintenancerequest` and its `description`, `work-details`, `receive`, `start` and `complete`, `DELETE /api/maintenancerequest/{id}`, `/api/maintenancerequestdigitalasset…`, and changing or removing a comment); deleting a conversation or a message.
- AC2: Given the same requests with a staff, board member, system administrator or support token, when they are called, then they behave as before.
- AC3: Given a member's token, when it calls a member endpoint (`GET /api/user/current`, `PUT /api/user/password`, `GET` and `PUT /api/user/profile`, maintenance requests, comments and photos on their own requests, their conversations and messages, their profiles and picture, published documents), then the API answers as L2-REQ-106 allows.
- AC4: Given no token, when any of these endpoints that is not anonymous is called, then the API answers 401 as before.
- AC5: Given a refused request, when the API answers, then the body says "Access denied." and names no data.

### L2-REQ-106: A Member's Data Is Scoped to Its Owner

**Traces to:** L1-REQ-021

On every admin screen a member can open, the API shall return a member only their own maintenance requests, comments, conversations, messages and profiles, and refuse with 403 any request that names another household's. The office keeps seeing everything it sees today. A member's own data means data tied to one of the profiles their user owns. The office for this rule is a caller with Write or higher on the aggregate concerned, as for photos and profile pictures (L2-REQ-089, L2-REQ-091); in the seeded roles this is exactly the office of L2-REQ-104.

**Acceptance Criteria:**

- AC1: Given a member, when they call `GET /api/maintenancerequest` or `/api/maintenancerequest/page/{size}/{index}`, then only requests made from their own profiles are returned; the office gets every request.
- AC2: Given a member, when they call `GET /api/maintenancerequest/{id}` for another household's request, then the API answers 403; for their own request it answers 200.
- AC3: Given a member, when they list comments (`GET /api/maintenancerequestcomment`) or read one by id, then only comments on their own requests are returned; adding a comment to another household's request is refused with 403.
- AC4: Given a member, when they send a maintenance request (`POST /api/maintenancerequest`), then it is recorded as requested by their own current profile, whatever profile the body names.
- AC5: Given a member, when they call `GET /api/conversations/by-profile/{profileId}`, then the API answers with the conversations of that profile only if it is theirs, refuses another person's profile with 403, and for the empty identifier (`00000000-0000-0000-0000-000000000000`) returns every conversation they take part in; the office gets every conversation for the empty identifier and the named profile's otherwise.
- AC6: Given a member, when they read a conversation or its messages (`GET /api/conversations/{id}`, `GET /api/messages/by-conversation/{id}`, `GET /api/messages/{id}`), send to it (`POST /api/conversations/{id}/messages`, `POST /api/conversations/{id}/send`) or mark it read, then the API allows it only when one of their profiles takes part; otherwise it answers 403. A message they send is always sent from their own profile.
- AC7: Given a member, when they start a conversation (`POST /api/conversations`, `POST /api/conversations/create`), then one of their own profiles is always a participant.
- AC8: Given a member, when they call `GET /api/profiles`, then only their own profiles are returned; `GET /api/profiles/{id}` and `GET /api/profiles/by-user/{userId}` for another person are refused with 403.
- AC9: Given a member, when they create a member profile (`POST /api/members`, onboarding), then it is created for their own user; when they change one (`PUT /api/members`), then only their own profile may be changed and another is refused with 403.
- AC10: Given a member, when they list documents (`GET /api/document`) or open one by id, then only published documents are returned; a draft is refused with 403.

### L2-REQ-107: Members Use Maintenance on the Admin Site

**Traces to:** L1-REQ-021

The admin Maintenance screen shall give a member what the public Requests page gave them: their own requests (L2-REQ-030, L2-REQ-106), sending a request (L2-REQ-021), progress in plain words (L2-REQ-088), comments (L2-REQ-028) and photos (L2-REQ-089). The screens are drawn in `docs/mocks/pages/admin-member-maintenance/` and `docs/mocks/dialogs/admin-member-maintenance-create/`.

**Acceptance Criteria:**

- AC1: Given a member on Maintenance, when it loads, then only their own requests are listed, with the filters All, New, Received, Started and Completed; with none, the page says "No requests yet" and offers "New request".
- AC2: Given a member opening their request, when the detail shows, then it shows its details, description, comments and photos, and offers no "Receive request", "Start work", "Finish work" or "Edit description".
- AC3: Given the create dialog, when anyone opens it, then its labelled "Photos (optional)" picker accepts several photos, lists each chosen photo by name with a "Remove" button and shows the hint "JPEG, PNG or WebP, up to 10 MB each." (L2-REQ-089 AC1, AC2).
- AC4: Given a request with photos is sent, when "Send request" is activated, then it reads "Sending…" and the dialog's controls are disabled until the request and every photo are sent; the new request then lists the photos (L2-REQ-089 AC3). If a photo fails after the request is created, the dialog closes and the page says "Your request was sent, but a photo could not be added. Open the request to try again." (AC4).
- AC5: Given a member on their own request's detail, when they choose "Add a photo", then it is sent and shown; while sending the control reads "Adding photo…"; if it fails the detail says "The photo could not be added. Please try again." (L2-REQ-089 AC5).
- AC6: Given the create dialog's Title or "What is wrong?" is empty, when the member sends, then nothing is sent and each empty field says what to write.

### L2-REQ-108: Members Manage Their Profile on the Admin Site

**Traces to:** L1-REQ-021

The admin "My profile" screen (`/profile`) shall give every signed-in person, members included, the profile picture of L2-REQ-091 and the notice choice of L2-REQ-092 for their own profile, beside the editing, Change password and Sign out it already has. The screens are drawn in `docs/mocks/pages/admin-member-profile/`.

### L2-REQ-109: The Member View Is Accessible

**Traces to:** L1-REQ-021

Every admin screen a member can open shall meet WCAG 2.2 AA for an audience of older women: keyboard access, visible focus, large targets and reflow at 400% zoom.

**Acceptance Criteria:**

- AC1: Given a member using only the keyboard, when they move through the sidebar, the tab bar, the Maintenance screen, its create dialog, Documents, Messages and My profile, then every control is reachable with Tab in reading order, operable with Enter or Space, and shows a visible focus ring; the create dialog keeps focus inside it and Escape closes it.
- AC2: Given a member, when they move between screens, then the current sidebar link and tab carry `aria-current="page"` and the skip link moves focus to the main content.
- AC3: Given any member screen, when it renders, then every link in the sidebar and tab bar, and every button, checkbox and file picker the member uses, is a target at least 44 px tall, the design system's comfortable target (`--target-comfortable`). Raising the admin's targets to 48 px would resize the office's screens too and is deferred (`docs/detailed-designs/admin-app/member-areas-by-role/README.md`).
- AC4: Given any member screen at a viewport 320 CSS px wide, when it loads, then it reflows to one column without horizontal scrolling and every control stays inside the viewport (L2-REQ-090).
- AC5: Given an error, a refusal or a saved change, when it is shown, then it is announced (`role="alert"` or a polite status) in plain words that say what to do next.
