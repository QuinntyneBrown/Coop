Pattern · Feedback

Notifications

The admin tells staff that a change worked with a short message at the top of the screen they changed, and shows work that is waiting as a count on the dashboard. Messages stay put until the next change, so nobody has to read quickly.

Overview

The admin has two notification surfaces. Neither floats, moves or times out.

  • Saved message: a success alert (.alert.alert--success) inside a polite live region, placed under the page header and above the content it reports on. It confirms a save or a send in one sentence that names the thing and says where it now is: "“About us” is now on the website."; "“Autumn courtyard gathering” is published and sent to members who asked for notices." It stays until the next change on that screen replaces or clears it, or the person leaves the screen.
  • Waiting count: a metric card on the dashboard that counts what needs attention, such as "2 Unread messages", and opens the list it counts.

The system also has a toast and a page banner. They are core options the admin does not use: every admin result belongs to the screen where it happened, and a message that disappears on a timer is easy to miss for anyone who reads slowly or looks away from the screen. The admin has no push notifications, notification centre or e-mail digest.

Failures are not notifications. A save that did not work is reported where the person can fix it, inside the form or dialog (see forms and feedback and loading).

Rules

  • One message per screen. A new save replaces the old message; starting another change clears it. Messages never stack.
  • No timers. A saved message never dismisses itself, so there is nothing to catch before it goes (WCAG 2.2.1). It also has no close button; the next action clears it.
  • Only after the server says yes. A saved message appears when the save has been confirmed, never in advance and never after a failure.
  • Counts are read when the dashboard loads. They are not live tickers and do not change while someone is reading the page.

Responsive behaviour

  • Saved messages are in the page flow, full width of the content column, at every size. The sentence wraps; nothing is cut off at 320px (400% zoom), and because the message is not fixed it never covers a field, a button or the phone tab bar.
  • Metric cards fill .metric-grid: one per row on phones, as many 14rem columns as fit above that. The number and label stay together.
  • Neither surface changes position or size with the theme.

Accessibility

Role and pattern

The saved message follows the status-message rule of WCAG 4.1.3: a role="status" container with aria-live="polite" that is in the page before anything is written into it. There is no WAI-ARIA APG pattern for it. A failure inside a dialog uses role="alert". The waiting count is a plain link built from metric card.

Keyboard

KeyAction
TabSkips the saved message, which holds no controls; reaches each metric card on the dashboard.
EnterOn a metric card, opens the list it counts.

Focus

A saved message never takes focus. After a dialog saves and closes, focus returns to the control that opened it; the message is announced on its own. Focus never moves to the top of the page to show a message.

Labelling

Icons are aria-hidden; the sentence carries the meaning. The sentence names the item in quotation marks so it makes sense out of context. The metric card's name is its own text, number first: "2 Unread messages".

Motion

Nothing animates. The message appears and disappears in place; the metric card's hover shadow changes over --duration-fast and is instant under reduced motion.

Touch

The whole metric card is the target, far larger than 44px. The saved message has no targets, so it cannot be tapped by mistake.

Content

  • Name the thing, then say where it is now: "“About us” is now on the website."; "“June Okonkwo-Baptiste” is now on the board list."
  • Say who received it when something was sent: "…is published and sent to members who asked for notices."
  • A failure says what did happen, what did not, and what to do: "“Autumn courtyard gathering” is published, but it was not sent to members. Press Save to try again."
  • No "successfully", no exclamation marks, no "Success!" title. The sentence is the message.
  • One sentence, full stop at the end. Add a second only when the person must do something next: "Use it the next time you sign in."
  • Count labels are plural nouns in sentence case: "Unread messages", "Open requests".

Do and don't

Sources

Extracted from these admin mocks:

  • Saved messages without a live region: admin-theme-saved/success, admin-profile-saved/success, admin-profiles-saved/success, admin-password-saved/success

Drift from the implemented admin

  • Visual language. The admin draws its messages in green with a Material Icons check_circle glyph and the Outfit font, light theme only. This system uses .alert.alert--success on the success tokens, an inline stroke SVG icon and both themes.
  • Four copies of one alert. Board, Pages, Website and Documents each style their own message: .board-alert--success, .pages-alert--success, .website-alert--success and .notice-alert--success. They behave correctly (a polite role="status" region present before the message). The system uses one .alert.alert--success for all of them.
  • Messages that are never announced. Theme, Profile, Profiles and Change password use the older .alert.alert-success with no live region, so screen-reader users get no confirmation.
  • Success after a failure. The Profile and Profiles screens show "Profile updated successfully" even when the API save fails, and Theme shows "Theme saved successfully" when the API fails because the theme is also stored locally (mock notes). The system shows a saved message only after the server confirms.
  • Errors left beside success. After Change password succeeds, the form resets but its "Current password is required" errors stay visible under the success message.
  • Wording. The older screens say "… saved successfully" or "… updated successfully" in a fragment without a full stop. The system writes a full sentence that names what changed, as the newer screens already do.
  • The unread count is not a link. The dashboard's .metric-card .metric-icon .metric-count .metric-label is a plain div; the count reads "Unread Messages" in Title Case. The system's metric card is an <a> to the Messages screen with the label in sentence case.
  • No toasts or push. The admin uses neither, and this system keeps it that way; toast and banner remain documented as core components only.
