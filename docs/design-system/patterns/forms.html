Forms

Every form in the Coop admin is one column of labelled fields, checked when it is sent, with the way out first and one primary button last. Staff and board members fill these forms in between other work, so each one asks only what it needs and says plainly what went wrong.

Overview

The admin has a handful of forms and each does one job: add a user, invite a member, log a maintenance request, write a document or notice, upload a file, add or edit a website page, change a password and save settings. They share one shape so nobody has to learn a second one.

  • Labels sit above fields, always visible, tied to the control with <label for>. Placeholder text is never the label.
  • Only optional fields are marked, with a quiet "(optional)" after the label. Everything else is required.
  • Checking waits for submit. Nobody sees red while still typing. After the first submit, each flagged field re-checks as it is edited, so its message goes as soon as it is fixed.
  • Errors are listed once, at the top, and again at each field. The summary links to the fields; each field says how to fix it.
  • The way out comes first, the primary button last, in .form-actions on a page or .dialog__footer in a dialog.
  • Removing something asks first, in a confirmation dialog that starts on the safe button.

Built from form field, text field, textarea, select, checkbox, switch, form layout, inline message, alert, button and dialog.

Structure

A form is a stack of .field blocks: label, then help, then the control, then the error. Related fields share a <fieldset> with a <legend>. The add-user dialog is the smallest complete example.

HTML
<form class="dialog__panel" novalidate>
  <div class="dialog__body stack">
    <div class="field">
      <label class="field__label" for="username">Username</label>
      <div class="field__help" id="username-help">The name they sign in with, such as neri.vale.</div>
      <input class="input" id="username" type="text" required aria-describedby="username-help">
    </div>
    <div class="field">
      <label class="field__label" for="role">Role</label>
      <select class="select" id="role"><option value="Member" selected>Member</option>…</select>
    </div>
  </div>
  <div class="dialog__footer">
    <button class="btn" type="button">Cancel</button>
    <button class="btn btn--primary" type="submit">Add user</button>
  </div>
</form>
  1. Form<form novalidate>: the admin writes its own messages, so the browser's bubbles are off.
  2. Field.field with .field__label, optional .field__help, the control, and .field__error when it fails. See form field.
  3. Group<fieldset> and <legend> around fields that belong together, such as a photo and its description.
  4. Error summary.alert.alert--danger.form-summary at the top of the form, only after a failed submit.
  5. Actions.form-actions or .dialog__footer: the way out first, the primary last, wrapping on narrow screens.

Checking and the error summary

On submit, every problem is found at once. The summary appears above the first field, takes focus and links to each field. Each failed field gets aria-invalid="true" and its own message, which says how to fix it. This is how the page editor already works.

MomentWhat happens
Typing, before the first submitNothing. No red borders, no messages.
Submit with problemsThe summary appears and takes focus; each failed field gets aria-invalid and a message; nothing is sent; nothing typed is cleared.
Editing a flagged fieldIt re-checks as it changes. When it passes, its message and red border go, and the summary loses that line.
Submit againThe summary is rebuilt, or removed when everything passes.
The server says noOn sign-in, one message for the whole form: "Username or password is wrong." Elsewhere, the message goes on the field that caused it. Values stay so a typo can be fixed.

Submitting

The pressed button shows its busy ring (aria-busy="true" and disabled) and keeps its width. Text fields turn readonly so what was typed stays readable; selects and checkboxes turn disabled. In a dialog every footer button and the close button are disabled until the request ends.

    Responsive behaviour

    • Forms are one column at every width. Fields that hold short values (an expiry date, a priority) may cap their width so the box matches the answer.
    • Two short related fields may sit side by side from 768px, such as a link's label and address in the website block editor. Below 768px they stack.
    • .form-actions and .dialog__footer wrap; the primary stays last, so on a narrow phone it lands on its own line.
    • Dialog forms become bottom sheets under 640px, with the footer sticky; see dialogs and overlays.
    • At 400% zoom (320 CSS px) every field is full width, labels wrap rather than truncate, and nothing scrolls sideways.

    Accessibility

    Role and pattern

    Native <form>, <fieldset> and <legend>, <label for>, <input>, <select> and <textarea>. A yes-or-no option is a native checkbox. The confirmation follows the WAI-ARIA APG Alert Dialog pattern.

    Keyboard

    KeyAction
    Tab / Shift+TabMoves through fields in reading order, then the actions.
    EnterIn a single-line field, submits the form. In a textarea, adds a new line.
    SpaceTicks or clears a checkbox; opens a select.
    Arrow keysChange the choice in a select.
    Enter on a summary linkMoves focus to the field with the problem.
    EscIn a dialog form, cancels and returns focus to the button that opened it.

    Focus

    On a failed submit, focus moves to the summary (tabindex="-1"), which is read out because it is role="alert". A dialog form puts focus on its first field. A confirmation dialog starts on the safe button, never the danger button.

    Labelling

    Every control has a visible <label for>; aria-label is not a substitute for a visible label. Help and error are tied to the control with aria-describedby, error first. Required fields carry the required attribute; optional ones say "(optional)" in the label. Sign-in and password fields use autocomplete (username, current-password, new-password) and allow pasting.

    Motion

    Border and ring colours change over --duration-fast, and the busy ring spins. Under prefers-reduced-motion the colour change is instant and the ring stops after one turn; the message still appears.

    Touch

    Fields, selects and buttons are 44px tall (--control-height-md); checkbox rows are at least 24px with the whole label clickable. There are at least 12px between the footer buttons.

    Content

    • Labels are short nouns in sentence case: "Username", "Page title", "Expires". A label may be a plain question when that is clearer: "What is wrong?".
    • Help text is a hint, not a rule list: "The name they sign in with, such as neri.vale." Give it only where a wrong entry is likely.
    • Field errors say how to fix it: "Give the page a title", "Type a username, such as oren.reed". Not "Username is required".
    • Summary titles count the work: "One thing needs attention", "Two things need attention before the page can be saved".
    • Submit buttons say what happens: "Add user", "Create invitation", "Send request", "Save page", "Upload file". Never "Submit" or "OK".
    • Confirmations ask a question that names the thing ("Remove “Our garden”?"), say what happens next, and label both buttons with outcomes: "Keep the page" and "Remove page".
    • Failures reassure first: "We couldn't save the page. Everything you typed is still here. Try again."

    Drift from the implemented admin

    • Visual language. The admin's .btn .btn-primary and .btn-secondary are green with an 8px radius in Outfit; the system's buttons are violet pills (.btn--primary, .btn) in the system's rounded sans. Fields are 44px tall with a --radius-md corner.
    • Field classes. .form-group, .field-help, .error-message and .field-error map to .field, .field__help and .field__error. .modal-actions, .btn-row, .page-dialog__footer and .content-dialog__footer map to .form-actions or .dialog__footer.
    • Labels not tied to controls. The add-user, maintenance, invitation and document dialogs and the change-password page put a bare <label> next to the control and copy its text into aria-label. The system uses <label for>, as the page editor already does.
    • Invalid states that show nothing. admin-user-create/invalid and admin-maintenance-create/invalid render the same as default: no message, no aria-invalid. Change password shows .error-message text ("Current password is required") that is not linked to its field and does not say how to fix it. The system uses the page editor's summary-plus-field model everywhere.
    • Busy without a cue. Change password's submitting state only disables the button; document create changes the label to "Saving…" without aria-busy. The system uses .btn[aria-busy="true"] on every submit.
    • Generic button labels. "Submit", "Create", "Save" and "Delete" become outcomes: "Send request", "Add user", "Create invitation", "Save document", "Delete mira.fern".
    • Title Case headings. "Add New User", "New Maintenance Request", "Create Invitation" and "Confirm Delete" become sentence case: "Add a user", "New maintenance request", "Invite a member".
    • Role option mismatch. The add-user role select offers "Admin" while the users table shows SystemAdministrator. The system labels the option "System administrator" and keeps the stored value. Likewise the maintenance category "HVAC" reads "Heating and cooling", and the placeholder options "Select priority" and "Select category" read "Not set", because both fields are optional.
    • Settings. "Reset to Default" is an <a> with no href, so it cannot be reached by keyboard; the system uses a ghost button. Colours are typed as hex text with a swatch beside them; recorded, unchanged here.
    • Success after failure. The theme and profile forms show their success message even when the save fails, and change password keeps its required-field errors visible after a successful save. The system shows success only after the server confirms, and clears errors on success. See feedback and loading.
