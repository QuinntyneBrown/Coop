Pattern

Forms

Every form in Coop stacks label, field and error in a form group, validates on the client for guidance only, and ends in one primary button that goes busy while the request runs.

Overview

The forms pattern covers the screens and dialogs where a person types values and submits them: sign in, create account, forgot password, change password, the onboarding steps, and the create dialogs for maintenance requests and users. It is built from form field, button and alert.

  • The label sits above its field, never beside it or inside it.
  • A field error sits directly under its field and appears only after the field has been touched. The field border turns red at the same time.
  • The submit button is never disabled for invalid input. It is disabled only while the request is in flight, and its label changes to say so.
  • A failed request shows one form-level message above the button row.

When to use

Use a form when the person supplies two or more values, or one value that needs validation, and the result is saved or sent together. For a single confirmation use a confirm dialog instead (see Dialogs). For a single filter or search use a search bar or filter chips, which apply as the person types.

Structure

A form is a stack of .form-group blocks followed by a button row. Each group holds a label, the control, and, when needed, a .error-message or .form-hint. Related fields that share a line, such as first and last name, sit in .form-row. The button row is .btn-row on pages and .modal-actions inside a dialog.

Password must be at least 8 characters long

Default form: label above field, optional hint under the field, secondary action left of the primary in a right-aligned .btn-row.
HTML
<form class="card" novalidate>
  <div class="form-group">
    <label for="username">Username</label>
    <input id="username" type="text" name="username">
  </div>
  <div class="form-group">
    <label for="password">Password</label>
    <input id="password" type="password" aria-describedby="password-hint">
    <p class="form-hint" id="password-hint">Password must be at least 8 characters long</p>
  </div>
  <div class="btn-row">
    <button type="button" class="btn btn-secondary">Cancel</button>
    <button type="submit" class="btn btn-primary">Create Account</button>
  </div>
</form>

Button placement

  • Pages with a card (change password, onboarding steps): .btn-row, right aligned, Cancel (secondary) then the primary action.
  • Dialogs: .modal-actions. The buttons share the width equally (flex: 1 1 0), Cancel first.
  • Auth pages (login, register): a single full-width primary button (.btn-full or .btn-block) with the alternative route as a text link below, for example "Don't have an account? Sign up".

States

A form moves through four visible states, taken from the login and register mocks. Validation text appears only for fields the person has touched; an untouched empty form shows no errors.

Default

Empty fields, enabled primary button. Shown in the structure example above.

Invalid (field errors)

Username is required
Password is required
Touched and empty. Border turns red, message sits under the field, the button stays enabled.

Cross-field rules use the same treatment on the dependent field. Register shows "Passwords do not match" under Confirm Password, and "You must accept the terms" under the terms checkbox.

Submitting

The primary button is disabled while the request runs and its label becomes a present-participle phrase. There is no spinner inside the button.

Error (request failed)

Invalid username or password
Public login and register put a red message block above the button. The admin login puts the same message in an .alert.alert-danger above the form (see Drift).

Forgot password has no implemented submitting, success or error presentation, and the dialogs close on submit without a busy indicator. These are not part of the pattern today.

Responsive behaviour

Forms are single-column at every width, so the field stack itself never reflows. What changes is the surrounding page.

The compiled CSS has no 640px or 1024px rule for forms. .form-row is a fixed two-column flex row with no wrapping rule, so use it only for short fields.

Accessibility

Role and pattern

Native <form> with native controls. Forms use novalidate because Coop draws its own messages; the server remains authoritative for every rule. A form-level failure message is a live region (role="alert").

Keyboard

KeyAction
Tab / Shift+TabMove through fields in reading order, then the button row.
EnterSubmit from any text field (native form behaviour).
SpaceToggle a focused checkbox; activate a focused button.

Focus

The design system draws one 2px focus ring on every control. The mocks removed the browser outline on inputs and relied on the border colour change alone, which fails WCAG 2.4.7 and 2.4.11; the ring is a design-system requirement, not source behaviour. After a failed submit, move focus to the first invalid field or to the form-level message.

Labelling

  • Every control has a visible label tied with for and id. The public app does this; the admin forms only carry aria-label on the input, which the design system treats as a minimum, not the pattern.
  • Mark an invalid field with aria-invalid="true" and point to its message with aria-describedby.
  • Never use the placeholder as the label.

Colour is never the only signal: the error text names the problem, and the invalid border is paired with aria-invalid.

Motion and touch

Only border-colour transitions (--duration-base). Controls are at least 2.5rem tall; the auth buttons are 3rem (.btn-lg height) or full width.

Content

  • Labels: noun phrases in sentence case, matching the data ("Username", "Confirm Password" in the mocks; the design system prefers "Confirm password").
  • Field errors: say what is missing or wrong, without blame: "Username is required", "Passwords do not match", "You must accept the terms".
  • Hints: state the rule before the person fails it: "Password must be at least 8 characters long".
  • Submit labels: the action as a verb phrase ("Sign In", "Create Account", "Update Password", "Submit Request"); the busy label is the same verb as a participle ("Signing in...", "Creating account...").
  • Request failure: one short sentence: "Invalid username or password".

Drift

  • The form-level request error is a red block in public login and register (.error-message-block) but an .alert.alert-danger in admin login. The design system keeps both as implemented; new forms use the alert, which carries a border and a role.
  • Busy labels differ: "Signing in..." (login), "Creating account..." (public register), "Creating..." (admin register), and no label change at all in admin change password. The design system requires a changed label.
  • Admin forms wrap the input in a label with no for and the review build added aria-label; public forms use for/id. The design system requires the for/id pair.
  • The admin Add New User dialog marks fields invalid with no explanatory text; admin settings and several profile forms do the same. Source gap, text required by this pattern.
  • After a successful admin password change, the form keeps its submitted flag, so required-field errors remain beside the success alert (see Feedback).
  • Inputs lose the browser outline on focus in the source; the shared focus ring replaces it.
  • Public profile edit and change-password expand an inline form below a button. The repository convention is a dialog or a separate screen; this pattern does not document the inline form as a variant.
  • Not implemented: inline spinner in the submit button, "copied" or success confirmation on forgot password, and validation on onboarding step navigation.
