Pattern

Navigation

Signed-in pages sit in an app shell: a fixed sidebar beside the content in the admin app, a top bar and bottom tab bar around the content in the public app. Landing and sign-in pages have no shell.

Overview

Navigation in Coop is flat: one level of destinations, always visible in the shell, with the current one marked. There are no breadcrumbs, no nested menus and no tabs-within-navigation. The parts are sidebar, top bar and bottom tab bar.

ShellUsed byParts
Admin shellDashboard, maintenance, documents, messages, users, roles, profiles, assets, invitations, settingsSidebar (10 destinations) beside a main column that starts with a page top bar
Public shellDashboard, requests, documents, messages, profile, onboardingTop bar, sidebar (5 destinations), main content, bottom tab bar (5 destinations)
No shellLanding, login, register, forgot password; admin change passwordPage content only, with links to the next page

When to use

  • Sidebar: a destination that a signed-in person returns to repeatedly. Ten admin destinations, five public ones.
  • Bottom tab bar: the five public destinations on touch screens. Admin repeats the same five (Home, Requests, Docs, Messages, Profile) on phones.
  • Top bar: the logo, a notification bell and the menu button on the public app; a page title, search and bell on the admin app.
  • No shell: anything a signed-out person sees, and one-off task pages such as change password. These link onward with text links ("Sign up", "Sign in", "Forgot password?") and a Cancel button.
  • Do not put a primary action in the navigation. Actions live in the page header (.page-header) as a button.

No shell: landing and sign-in

The landing page has a slim navbar (logo, "Sign In", and a primary "Get Started" or "Register" link) above a hero and content sections, and a footer. The tab bar pads its bottom by env(safe-area-inset-bottom), so it clears the home indicator on phones.

Accessibility

Role and pattern

Each group of links is a <nav> landmark with a distinct aria-label ("Admin", "Primary"). This is the WAI-ARIA landmark approach, not the menu pattern: items are plain links. The source navs have no labels, which the design system requires. Mark the current link with aria-current="page" in addition to the .active class.

Keyboard

KeyAction
TabMove through links in DOM order. Sidebar and tab bar items are links, each a tab stop.
EnterFollow the link.
EscRequirement for the public drawer: close it and return focus to the menu button.

A "Skip to content" link as the first focusable element jumps to #main. The sidebar must precede main in the DOM so the skip link is useful.

Focus

The shared focus ring applies to every link and icon button. When the drawer is open the page behind must be inert and focus must be trapped in the drawer (requirement; the source has neither).

Labelling

Icon-only controls (bell, menu) need an accessible name. Tab items keep their text label visible; do not hide labels at small widths.

Motion and touch

Link backgrounds fade over --duration-base. Tab items are at least 3.5rem wide and a tab-bar row is about 3.5rem tall; the 24px icon with a 11px label meets the 24px target-size minimum (2.5.8).

Content

  • Labels: one or two words, nouns: "Dashboard", "Maintenance", "Documents", "Messages".
  • Tab labels are shorter than sidebar labels: "Docs" for "Documents", "Requests" for "Maintenance" on the public app.
  • Same destination, same icon: home, build, description, chat, person across the tab bar and the sidebar.
  • Order: Home first, Profile last. Admin management items (Users, Roles & Privileges, Profiles, Assets, Invitations, Settings) follow the shared items.
  • Page title: the same words as the navigation label.

Drift

  • The design intent is a drawer below 768px, but the compiled CSS collapses the public sidebar below 1024px (drawer, behind a menu button) and the admin sidebar at 768px with no drawer. The design system documents both as implemented and requires an admin drawer or an equivalent route to the six admin-only destinations on phones.
  • Admin pages show a "hamburger" button in the dashboard header, but no mock captures a menu opening, so the design system does not document that behaviour.
  • Public and admin sign-in pages render the bottom tab bar on phones, linking to pages that need a session. The design system treats sign-in as shell-free and omits the tab bar there.
  • The public tab bar still displays at 1024px and above alongside the sidebar; the design system treats it as phone and tablet navigation only.
  • Public and admin use different sidebar class names (.sidebar-link and .nav-item), different landing navbars (.landing-navbar and .navbar), and different sidebar footers. components.css keeps both names with one look.
  • Sidebar, tab bar and icon buttons lack landmark labels and names in the source; labels are added in this pattern.
  • Not implemented: breadcrumbs, nested navigation, a notification list behind the bell, a 404 screen (unknown routes redirect to the landing page).
