Pattern · Navigation

Navigation and page structure

The Coop admin has one shell. From 768px a sidebar lists every section, with the current one highlighted. On phones a bottom tab bar holds the four places people go most and a "More" tab that lists every section. Every page starts with the same header: the title, a one-line summary and the page's actions.

Overview

The admin is wide but shallow: thirteen sections, each one a single page with its dialogs. People find their way by the sidebar, which never changes order, and by a page title that always matches the sidebar item they pressed. A member sees only five of them, Dashboard, Maintenance, Documents, Messages and My profile, in the same order (the sidebar's member variant); the office sections are left out, and typing one of their addresses opens the dashboard.

  • Sign-in shell: no navigation. A centred card (.auth-layout and .auth-card) under the co-op's mark. Sign in, register, forgot password and the first-time setup steps.
  • Admin shell: .app-shell with a sidebar and .app-shell__main. The sidebar holds the co-op's mark and name, the thirteen sections, and the signed-in person at the foot.
  • Phone shell: below 768px the sidebar is hidden and a bottom tab bar holds Dashboard, Maintenance, Documents and Messages, plus "More", a button that opens a dialog listing all thirteen sections and the signed-in person's profile. Every section is reachable at 320px.
  • Page header: .page-header with the <h1>, a one-line .subtitle, and the page's actions on the right: a search field and at most one primary button.
  • Inside a page: tabs split one page into panels (Settings: Theme, Content, Account); pill tabs filter a list (Maintenance: All, New, Received, Started, Completed).

Use tabs only when the panels share one page and one address is enough. Use pill tabs when every option shows the same list, filtered. Use a new sidebar section only when the task is a different job, not a different view of the same list.

Back behaviour

  • The sidebar is the way between sections. It is in the same place, in the same order, on every page.
  • The admin is two levels deep at most. A section's list and its dialogs, or a list beside its detail (Maintenance, Messages). There is no breadcrumb because there is nothing above the section to go back to.
  • Dialogs do not change the address. Closing one returns to the list, with focus on the button that opened it. The browser's back button leaves the section, as people expect.
  • Filters and tabs keep their own address where the admin has one (Maintenance's "Completed", Settings' "Account"), so a link or a refresh lands in the same place.
  • The co-op's mark goes to the dashboard.

  • Breakpoints are in rem (48rem), so a person who enlarges text gets the phone layout sooner, which is what they need.
  • Every section is reachable at every width: from the sidebar at 768px and up, from the tab bar or its "More" dialog below. Nothing in the navigation scrolls sideways at 320px.
  • Underline tabs scroll sideways inside their own row when they do not fit; they never wrap to two rows. Pill tabs wrap.

Accessibility

Role and pattern

The sidebar is an <aside> holding a <nav aria-label="Admin sections">; the tab bar is a second <nav> with its own label. "More" is a <button aria-haspopup="dialog" aria-expanded> that opens a modal dialog (WAI-ARIA APG Dialog pattern) holding a third labelled <nav> with the same links as the sidebar. Current pages use aria-current="page". In-page tabs follow the WAI-ARIA APG Tabs pattern with manual activation (role="tablist", tab, tabpanel). Every page has a skip link to #main.

Keyboard

KeyAction
TabSkip link first, then the sidebar links in order, then the page header's actions, then the content.
EnterFollows a sidebar or tab bar link.
Enter / Space on "More"Opens the sections dialog with focus on the current section.
EscCloses the sections dialog and returns focus to "More".
← / →In a tab list, moves between tabs; Enter or Space shows the panel.
Home / EndIn a tab list, goes to the first or last tab.

Focus

The shared focus ring shows on every link and tab. On the current sidebar item the ring sits outside the highlight so both are visible. After following a link, focus starts at the top of the new page; the skip link is the first stop. Opening "More" moves focus to the current section in the dialog; Tab stays inside the dialog until it closes; closing it returns focus to "More".

Labelling

Every link has visible text; icons beside it are aria-hidden="true". The two navs have different labels so a screen reader's landmark list makes sense. The page's <h1> matches the sidebar item's words, and the page <title> starts with the same words.

Motion

Link and tab backgrounds change over --duration-fast; nothing slides. Reduced motion makes the change instant.

Touch

Sidebar links and tabs are 44px tall (--target-comfortable). The tab bar is 64px tall with each tab, "More" included, a full-height target, and adds the device's bottom safe area. Links in the "More" dialog are 44px tall.

Content

  • Section names are short nouns and match the page title: "Maintenance" opens "Maintenance requests"; "Users" opens "Users".
  • The tab bar uses the sidebar's names and icons: "Dashboard", "Maintenance", "Documents", "Messages". The fifth tab is "More", and its dialog is titled "All sections".
  • The page summary is one line about the page's state: "2 open, 1 in progress.", "4 people can sign in to the admin.", "Pages visitors reach from the website menu."
  • Header actions are verbs that name the thing: "New request", "Add user", "New page", "Upload file", "Create invitation".
  • Roles are shown in words in the sidebar footer and tables: "System administrator", "Board member", "Member".

Drift from the implemented admin

  • Sidebar classes. .sidebar .sidebar-nav .nav-item.active with .sidebar-header, .logo and .sidebar-footer .user-info map to .sidebar, .sidebar__brand, .sidebar__nav .nav-link and .sidebar__footer. The section order is kept as implemented.
  • Current page by class only. The implemented sidebar and tab bar mark the current item with .active and no aria-current, and the <nav> elements have no label. The system uses aria-current="page" and labelled navs.
  • Icons read aloud. The Material Icons ligatures ("dashboard", "build", "admin_panel_settings") are text without aria-hidden, so each link's name starts with the icon's name. The system's icons are stroke SVGs with aria-hidden="true".
  • Phone layout. At 768px and below the implemented sidebar does not hide: it stacks above the page as a static block of all thirteen links, pushing every page's title down, and the bottom tab bar also shows on pages that include it (Users, Assets and Invitations do not). The system hides the sidebar below 768px (48rem), shows the tab bar on every page, and puts the full list behind its "More" tab, so every section is reachable at 320px.
  • Tab bar destinations and names. The implemented tabs are Home, Requests, Documents, Messages and Profile. "Home" (house icon) becomes "Dashboard", with the sidebar's icon; "Requests" stays, since "Maintenance" does not fit a phone tab; "Profile" moves into the "More" dialog's footer as "Your profile", and "More" takes its place.
  • Sidebar footer. Shows the username "mira.fern" and the role key "SystemAdministrator"; the system shows the display name "Mira Fern" and the role in words. The implemented .user-avatar uses a random inline background colour; the system's .avatar uses tokens.
  • Page headers. .page-header with .page-actions, .pages-header and .greeting-section become one .page-header with a .subtitle. Titles move to sentence case ("Maintenance Requests" becomes "Maintenance requests").
  • Search without a visible label. .search-input has only aria-label and a placeholder ("Search users..."). The system's .search keeps the aria-label, adds a magnifier and a clear button, and is documented on the search field page.
  • Tabs and filters. Settings' .tabs .tab.active .tab-content and the filters' .filter-tabs .filter-btn and .filters .filter-btn are buttons with an .active class and no roles. The system uses APG tabs (.tabs__tab[aria-selected]) and pill tabs for filters.
  • Visual language and logo. The green Outfit sidebar and the co-op logo's own fixed palette become the system's violet tokens; the three-circle mark is drawn with token fills so it follows the theme.
