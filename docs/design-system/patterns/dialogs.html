Pattern

Dialogs

Coop opens a modal dialog for short create forms, confirmations, quick detail and document viewing, and navigates for everything that is a place of its own.

Overview

A dialog interrupts the page to ask for one thing: fill in a short form, confirm a destructive action, glance at a record, or read a document. The page behind stays where it was and returns when the dialog closes. The visual component is documented in Dialog; this page describes when the product uses it and how dialogs combine.

  • One dialog answers one question. Its footer holds the answer: a primary action, a danger action, and a way out.
  • A dialog can open from a dialog once: asset delete confirmation opens over asset details.
  • Dialog results come back to the page behind them. The mocks show no toast and no confirmation banner for dialog results (see Feedback).

When to use

Use a dialog when the task is short, belongs to the list or page behind it, and is finished in one step. Navigate when the person works on something that has its own address, tabs or several steps.

Do not use a dialog for content that needs more than about one screen of fields, for a flow with more than one step, or for a message that is not a question.

Structure

The overlay (.modal-overlay) is a full-viewport scrim that centres its content at --z-modal. Inside it one .modal-content.card holds the title, the body and the action row. The examples below show the content panel without the fixed overlay so they sit in the page; the overlay adds the scrim and centring only.

Form dialog

Add New User

Create dialog: title, form groups, then .modal-actions with Cancel first. The panel is 400px wide (--layout-dialog-sm).

<div class="modal-overlay">
  <div class="modal-content card" role="dialog" aria-modal="true" aria-labelledby="title">
    <h3 id="title">Add New User</h3>
    <form novalidate>
      <div class="form-group">…</div>
      <div class="modal-actions">
        <button type="button" class="btn btn-secondary">Cancel</button>

      </div>

States

StateWhat the product does
ClosedNothing rendered. The trigger button on the page is the only trace.

InvalidForm dialogs mark touched fields invalid as in Forms. Maintenance create shows red borders; admin user create shows none with text.
BusyOnly asset upload has a busy state in the mocks. Other dialogs close on submit and show no pending indicator.
EmptyPublic maintenance detail has an empty state when the request has no comments yet.
StackedAsset delete confirm over asset details. No other pair exists.
Closed after submitSeveral create dialogs (document, asset upload, invitation) close even when the request failed, and no failure message is shown.

Responsive behaviour

  • The overlay pads the panel by --space-4 on every side, so the panel is the viewport width minus 32px on phones. The panel is capped at 400px (confirm, short forms), 500px (.modal-md) or 700px (.modal-lg).
  • The panel is capped at 90vh and scrolls inside itself. The scrim does not scroll.
  • The compiled CSS has no @media rule for dialogs: there is no full-screen sheet on phones and no bottom-sheet variant.
  • The mobile tab bar sits below the overlay (--z-sticky against --z-modal) and is covered by the scrim.
  • .modal-actions buttons share the row equally, so three actions (asset details) get narrow at 320px; keep labels to one word.

Accessibility

Role and pattern

WAI-ARIA Modal Dialog: role="dialog" (or alertdialog for confirms), aria-modal="true" and aria-labelledby pointing at the title. The source dialogs have none of these attributes; the design system requires them. The examples above use role="group" only because they are static samples, not open dialogs.

Keyboard

KeyRequired behaviourIn the source
Tab / Shift+TabCycle through the dialog's controls only.Not implemented: focus can leave the dialog.
EscClose the topmost dialog.Not implemented in general.
EnterSubmit a form dialog; activate the focused button.Native form behaviour.

Requirements, not implemented behaviour: move focus into the dialog on open (the title or first field; the Cancel button for a confirm), trap focus, make the page behind inert, close on Esc, and return focus to the trigger on close. With a stacked dialog, Esc closes only the topmost one and focus returns to the control that opened it (the Delete button in asset details).

Labelling

Every dialog has a visible title that labels it. Icon-only close buttons need an accessible name ("Close"); the public "×" button in the source has none beyond the glyph.

Motion and touch

The source dialogs appear without animation, which needs no reduced-motion handling. Action buttons are at least 2.5rem tall.

Content

  • Titles: Title Case in the mocks ("Add New User", "Confirm Delete", "Asset Details", "Invitation Created"); the design system uses sentence case for new dialogs.
  • Confirm body: "Are you sure you want to delete this {thing}?" Name the thing; do not add a second sentence.
  • Buttons: the verb the person chose ("Delete", "Create", "Submit Request", "Close"). Avoid "OK" and "Yes".
  • Order: Cancel or Close first, the primary or danger action last, except asset details, which leads with Delete.

Drift

  • Public dialogs use a .modal panel with a .modal-header and .close-btn; admin dialogs use .modal-content.card with no close control. The design system uses .modal-content.card everywhere and requires a close control only on viewers.
  • Overlay scrim and panel width differ by page (400px, 500px, 700px, a 40% or 50% black scrim in the source); the design system takes the width from --layout-dialog-* and the scrim from --color-bg-backdrop.
  • No dialog traps focus, makes the page inert, handles Esc, or restores focus. The Accessibility section states these as requirements.
  • The admin user edit dialog submits through the create handler, and some create dialogs close even on failure; neither is a pattern to copy.
  • Not implemented: full-screen sheets on phones, dialog animation, a dialog with more than one step.
