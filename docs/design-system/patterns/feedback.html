Pattern

Feedback

Coop tells people what happened in the page itself: a green alert after a save, red text under a field, a centred message for an empty list, a spinner while a list loads. It has no toasts, skeletons or notification centre.

Overview

Four kinds of feedback exist in the product. Each is a block in the normal page flow: nothing floats, nothing disappears on a timer.

  • Success: alert with the success colours, shown at the top of the card that was saved.
  • Error: red text under a field (.error-message) and, for a failed request, one red block above the submit button. See Forms.
  • Empty: an empty state (large icon and one line) where a list would be.
  • Loading: a spinner centred above the page content while a list loads.

The mocks also show where feedback is missing. Those gaps are listed under Sources and are not designed here.

Empty state

build

No maintenance requests found

Empty state: one icon, one sentence, centred in the area where the list would be. The same markup serves "nothing yet", "no results for this filter" and "the fetch failed".

Loading

The spinner sits above the page header and filters while the list loads. Nothing replaces the list with grey placeholders.

Responsive behaviour

Feedback blocks are full width inside their container and have no @media rules of their own.

  • Alerts and error blocks wrap their text and grow in height; they never truncate.
  • An empty state centres in whatever width the list area has (padding: var(--space-12) var(--space-5)).
  • The spinner is centred in its row at every width.
  • At 768px and below, a success alert at the top of an admin page scrolls with the page; nothing is pinned above the tab bar.

Accessibility

Role and pattern

Use live regions so assistive technology announces feedback that appears without a page load: role="status" for a success alert and the spinner, role="alert" for a request failure. Field errors are linked with aria-describedby and do not need a live role. The source has none of these roles; they are design-system requirements. A live region must exist in the DOM before its text is inserted.

Keyboard and focus

Feedback blocks are not interactive and take no focus. After a failed submit, move focus to the first invalid field or to the failure message, as described in Forms.

Labelling

  • The empty-state icon is decorative (aria-hidden); the sentence carries the meaning.
  • The source spinner is an empty div with no name. The design system requires a role and a label ("Loading").
  • Never rely on colour alone: success and error each carry a sentence.

Motion

The spinner rotates continuously (--duration-spin). Under prefers-reduced-motion the design system stops the rotation and keeps the labelled static ring. The source has no reduced-motion rule.

Content

  • Success: "{Thing} {past participle} successfully": "Password updated successfully", "Profile updated successfully", "Theme saved successfully". No exclamation mark (the public profile line has one).
  • Failure: say what failed in plain words, no codes: "Invalid username or password".
  • Empty: "No {things} found". The mocks use the same sentence for an empty list and a filter with no match; write a second sentence only when the next step is obvious.
  • Do not use "Oops", "Whoops" or apologies; do not repeat the same message in a field and in a banner.

Do and don't

Sources

  • Gap records: docs/mocks/README.md, "Known implementation gaps" and manifest.json not_applicable notes.

Source gaps (not designed here)

  • No error banner for a failed fetch on any list or dashboard; the page renders empty or keeps old data.
  • No failure feedback for failed saves, creates, uploads, invitation creation, and failed message sends. Profile, profiles and theme saves report success regardless.
  • No loading indicator for dashboards, forgot password, onboarding steps, or dialog submits (only asset upload has a busy state, with a progress bar stuck at zero).
  • No "copied" indicator for the invitation token, no 403 or 500 page, no offline state.
  • Not implemented and not proposed: toasts, skeleton screens, a notification centre, an Undo.

Drift

  • Public profile uses a plain .success-message line, not an alert; the design system uses .alert.alert-success for both apps.
  • Admin change password keeps its submitted flag after success, so "required" errors stay beside the success alert. The pattern requires clearing field errors on success.
  • The sign-in failure is a red block in public and a .alert.alert-danger in admin.
  • The empty list and the no-results list share one sentence in the source.
  • The admin unread badge (.notification-badge) is not in components.css; it is documented here as an indicator only, not as a pattern.
