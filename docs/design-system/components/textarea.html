Textarea

A multi-line box for words that need room: what is wrong in a maintenance request, the introduction on the home page, a photo description, the text of a whole page.

WCAG 2.2 AAStatus: stableNative <textarea>

Overview

Put .textarea on a native <textarea> inside a form field. Use it whenever a good answer is a sentence or more. For a few words (a title, a name) use a text field.

It appears in three admin dialogs:

  • New maintenance request: "Description", under the request's title.
  • Website editor (Edit hero and the other website sections): "Introduction (optional)" and "Photo description", three rows each.
  • Page editor (New page, Edit page): "Photo description" (three rows) and "Page text" (eight rows), with help that lists the simple HTML tags the page accepts.

Anatomy

  1. LabelA short noun phrase in sentence case, from the form field.
  2. Help (optional)Says who reads the text or what it may contain.
  3. Text--text-body (16px) with --line-height-relaxed for easier reading back.
  4. Resize handleVertical only (resize: vertical); the box never gets wider than its field.

Variants

One look. What changes is the label, the help and the number of rows.

Plain words work. For headings and lists use simple HTML: <h2>, <p>, <ul>, <li>, <strong>, <a>, <img>.
A maintenance request description, an optional introduction and the long page text with its help.
HTML
<div class="field">
  <label class="field__label" for="page-body">Page text</label>
  <div class="field__help" id="page-body-help">Plain words work. For headings and lists use simple HTML: …</div>
  <textarea class="textarea" id="page-body" name="body" rows="8" required
            aria-describedby="page-body-help"></textarea>
</div>

Sizes

There is no size modifier. Height comes from rows, with a floor of 2.5 × --control-height-md (110px) so even a short box is an easy target.

rows="3" for descriptions and introductions, rows="8" for a whole page of text.

Same states and tokens as the text field. Hover and focus are forced with data-state.

  • Invalid applies to a required textarea left empty: the page text, a photo description when the page has a photo, a maintenance description.
  • Read-only is the saving state: while the dialog says "Saving…", the text stays on screen, readable and selectable, until the save finishes.
  • Disabled is for a box that does not apply right now. Do not use it while saving.

Responsive behaviour

  • Full width of the field at every size; in a dialog that is the whole dialog body.
  • Rows stay the same on phones and desktops. The box can be dragged taller; it never scrolls sideways, even at 320px or 400% zoom.
  • Long words, pasted web addresses and HTML tags wrap inside the box.

Theming

Shares --field-bg and --field-border with .input, so every state and both themes match the text field exactly. The only textarea-specific values are the minimum height and --line-height-relaxed.

Accessibility

Role and pattern

Native <textarea> (a multi-line textbox), labelled by <label for>. Help and error join through aria-describedby, error first.

Keyboard

KeyAction
Tab / Shift+TabMoves to the next or previous field. Tab never inserts a tab character.
EnterInserts a new line. It does not submit the dialog, so half a page cannot be saved by accident.

Focus

Focus border plus the shared ring with no offset, as on the text field. After a failed save, the error summary's link moves focus into the textarea.

Labelling

Every textarea has a visible <label for>. Help that lists HTML tags is plain text in .field__help, read after the label, so a screen reader user hears which tags are allowed before typing.

Motion

Touch

Content

  • Label with a short noun phrase: "Description", "Introduction", "Photo description", "Page text".
  • Help says who reads the text or what it may hold: "Describe the photo for people who cannot see it." "Plain words work."
  • Errors say what to write: "Write something for the page", "Describe this photo for people who cannot see it". Not "Required".
  • No minimum length and no counter; the admin sets no limits that need one.

Drift from the implemented admin

The implemented admin is green, set in Outfit, light theme only; this page adopts the system's violet, rounded system fonts and both themes. Textarea-specific drift:

  • Type. The page editor sets the page text in 14px monospace with a 180px minimum height; the photo description is 15px with a 96px minimum; New maintenance request uses 14px with an 80 to 100px minimum. The system uses 16px --text-body, --line-height-relaxed and one 110px minimum, with height set by rows.
  • Labelling. New maintenance request's "Description" has a label without for and an aria-label copy, and no rows. The page and website editors label correctly.
  • Errors. New maintenance request shows only a red border on a touched empty description, with no text. The page and website editors use aria-invalid, .field-error and aria-describedby, matching the system apart from the Material icon.
  • Help position. The editors put .field-help below the textarea at 13px; the system puts .field__help above it at 14px.
  • Saving state. The page editor leaves textareas editable while "Saving…"; the website editor disables them. The system makes them read-only.
  • Focus and border. Same as the text field: no outline, a pale border under 3:1 and an 8px radius.
