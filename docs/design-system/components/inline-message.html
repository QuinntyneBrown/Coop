Inline message

One short line right next to the thing it is about. Field help says what to enter, a field error says how to fix one answer, and an inline status says a change is saving, then saved.

Overview

Inline messages belong to one field or one card. Many people who run OWN Housing Co-op read slowly and carefully, so the message sits where their eyes already are, in plain words.

  • Field help (.field__help): a hint that is always there, such as "Use at least 8 characters." on a new password, or "JPEG, PNG or WebP, up to 10 MB." on a photo upload.
  • Field error (.field__error): appears under one field after Save or Create finds a problem with it. When a form has more than one problem, also show a summary at the top of the form; see alert and form layout.
  • Inline status (.inline-status): "Saving…" then "Saved just now" beside a card title, for a change saved in place. The admin confirms most saves with a toast today; use the inline status only when the person stays on the same card.

News that is not about the element beside it, such as "We couldn't save your changes. Try again.", is an alert, not an inline message.

Anatomy

  1. Help text.field__help: small body text in --color-fg-muted, always shown, linked with aria-describedby.
  2. Error glyph⚠ from .field__error::before; the words, not the glyph, carry the message.
  3. Error textSmall body text in --color-danger-fg; its id comes first in the field's aria-describedby.
  4. Invalid fieldaria-invalid="true" thickens the border in --color-danger-solid; colour is never the only signal.

Variants

Help explains before anyone makes a mistake. An error explains after. A status reports on a save. A field can carry help and an error together.

Sizes

Help, errors and status all use small body text (--text-body-sm, 14px) under every size of field.

States

Inline messages are not interactive. They follow the state of their field or of the save.

  • Help is always visible. It never disappears when the field gets focus or text, unlike a placeholder.
  • Field errors appear after Save, Create or Update password, never while someone is still typing. They clear when the field is valid on the next try.
  • Disabled: while a dialog saves (content editor busy), fields are disabled and help stays readable in --color-fg-muted.
  • Saving… shows the pulsing dot until the server answers; then Saved just now replaces it in the same element, so it is announced once.

Responsive behaviour

  • Help and errors are as wide as their field and wrap onto as many lines as they need; at 320px and at 400% zoom nothing is cut off.
  • The ⚠ glyph stays on the first line of a wrapped error.
  • In two-column rows (a button's Label and Address in the content editor) each message stays under its own field; when the row stacks on phones, the message moves with it.
  • An inline status sits at the end of the card's title row (.cluster--between) and wraps under the title on a narrow card.

Theming

Help reads --color-fg-muted; errors read --color-danger-fg, and the invalid border --color-danger-solid; inline status reads --color-fg-muted, or --color-success-fg with --success. The dot is currentColor, so it always matches its text. Each colour is tuned per theme to stay above 4.5:1 on the page, on cards and inside dialogs.

Accessibility

Role and pattern

Help and errors are plain text tied to their control with aria-describedby; an error also sets aria-invalid="true" on the control (WCAG 3.3.1, 3.3.3). The label is a real <label for>, not an aria-label. An inline status is a role="status" live region that exists before the save starts, so the change of text is announced politely (4.1.3).

Keyboard

KeyAction
TabMessages are not stops. Focusing a field reads its label, then its error, then its help.
Enter on a summary linkMoves focus to the field the error is about.

Focus

After a failed Save with several problems, focus moves to the error summary at the top of the form; each summary item links to its field. With one problem, focus moves straight to that field. The inline status never takes focus.

Labelling

Put the error id before the help id in aria-describedby, so the problem is read first. The ⚠ comes from CSS content; some screen readers say "warning sign" and the sentence still makes sense. Hide the ✓ in "Saved" with aria-hidden.

Motion

The status dot pulses once per --duration-loop (1.4 s). Under reduced motion it runs one cycle and stops; the word "Saving…" still says what is happening.

Touch

No targets of their own. Links inside help text, if any, follow the link rules.

Content

  • Errors say what to do, in a short sentence: "Give the director's name.", "Give the page a title.", "Write something for the page."
  • Name the field in its own words when the label is not obvious: "Fill in “Title”.", "Describe this photo for people who cannot see it."
  • Prefer the fix over the rule. Write "Type your current password." rather than "Current password is required", and "These passwords don't match. Type the same new password in both boxes." rather than "Passwords do not match".
  • Help states limits and examples: "Use at least 8 characters.", "JPEG, PNG or WebP, up to 10 MB.", "A page on this site such as /#visit, a web address, an e-mail address or a phone number."
  • Status: "Saving…" (with the ellipsis character), then "Saved just now".

Drift from the implemented admin

  • Add New User, invalid: touched invalid fields only turn red; there is no error text at all, and the fields are named by aria-label with an unlinked <label>. The system adds a .field__error per field, aria-invalid, and <label for>.
  • Change Password, invalid and mismatch: errors are .error-message divs in a bright red, not linked with aria-describedby, and the fields do not set aria-invalid. Copy states the rule ("Current password is required", "Passwords do not match"). The system uses .field__error, links it, and states the fix.
  • Change Password: the rule "Password must be at least 8 characters long" is a .password-hint paragraph above the form, linked to no field. The system moves it to .field__help under New password.
  • Content, director and page editors: .field-help and .field-error are already linked and set aria-invalid, which the system keeps. The error glyph is the Material Icons error_outline font; the system uses the CSS ⚠ glyph. On Photo description the help id comes before the error id in aria-describedby; the system reads the error first.
  • Sizes and colours: implemented help is 13 to 14px and errors 14 to 15px, in the green-and-Outfit admin palette with three different reds. The system uses one size (--text-body-sm) and one danger colour per theme.
  • Inline status: the admin has no in-place "Saving…" status; saves end in toasts (for example Website saved). The variant is part of the system for in-place saves and is not yet used by the admin.
