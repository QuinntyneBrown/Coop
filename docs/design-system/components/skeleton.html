Skeleton

Soft grey shapes laid out like the content that is coming, with a gentle shimmer. They show where things will be, so the page does not jump when the data arrives.

Overview

The Coop admin shows a spinner with words for every load today. The skeleton is a core part of the system for when the layout is known in advance and a spinner would make the page jump: the four metric cards on the Dashboard, a row of the Users table, or a request in the Maintenance list.

  • Keep the real page chrome (sidebar, page title, Add User, the search field) and swap only the data for skeletons.
  • Choose one loading treatment per region: a skeleton or a spinner, never both.
  • For an action in progress (saving, uploading), use a busy button, a spinner or a progress bar, not a skeleton.
  • If loading fails, replace the skeletons with a danger alert or an error empty state that offers Try again.

Anatomy

  1. CircleA .skeleton at the icon's exact size, fully rounded (the metric-card icon is 56px).
  2. Title bar.skeleton--title: 1.5em tall; here narrowed to a number's width.
  3. Text line.skeleton--text: 1em tall; the last line in a group is 60% wide.
  4. Busy containerThe real card with aria-busy="true" and an aria-label that says what is loading.

Variants

Pick the shape that matches what will replace it: a line of text, a heading, a circle for an avatar or icon, or a block for anything else.

Title, text lines, circle (an avatar) and block (a notice preview).

Sizes

Text and title skeletons are sized in em, so they follow the font size of where they sit and grow when someone zooms in. Circles and blocks take the size of the real thing, set with tokens: --size-avatar-sm for a table avatar, --size-avatar-lg for a metric-card icon. Widths of single lines can be narrowed to the expected text (a number, a username).

States

A skeleton has one state, loading. The container moves from loading to loaded, or to failed.

New

Both themes

  • Loaded: remove aria-busy and the busy aria-label, and swap skeletons for content in one paint, so screen readers read the finished section once.
  • Failed: replace the whole region with a danger alert that says what did not load and offers Try again ("We couldn't load the users list. Check your connection and try again.").
  • Empty: if the data comes back empty, replace the skeletons with an empty state, not with zeroes in placeholder shapes.

Responsive behaviour

  • Skeletons live inside the real layout (the metric grid, the table, the list), so they reflow exactly as the content will.
  • Draw only what fills the first screen: four metric cards, or about five table rows. Do not draw a whole list.
  • Fixed widths stay well under 320px (a username line is 6rem) so nothing overflows a phone; a table of skeleton rows scrolls inside its .table-wrap like the real table.

Theming

The shimmer is a gradient between --color-bg-subtle and --color-bg-subtle-hover, both tuned per theme, so skeletons are a quiet grey on light cards and a lifted grey on dark ones. Nothing in the component changes between themes.

Accessibility

Role and pattern

Every skeleton is aria-hidden="true". The region that is loading carries aria-busy="true" and an aria-label ("Loading users", "Loading maintenance requests"), so assistive technology knows it is not ready and does not read half a page. There is no WAI-ARIA widget pattern; this is the aria-busy state on a region.

Keyboard

KeyAction
TabSkips skeletons. Real controls in the chrome (sidebar, search, Add User) stay reachable while the data loads.

Focus

Skeletons never take focus. When content arrives, focus stays where it was.

Labelling

The busy region says what is loading in words. Keep the page <h1> real ("Users", "Dashboard") so the page is identified from the start. A table keeps its real header row and caption.

Contrast

Skeletons are decorative placeholders and are exempt from 1.4.11. The content that replaces them uses the normal pairs:

Loaded text on a card
Loaded secondary text on a card

Motion

The shimmer runs once per --duration-loop (1.4 s) and is soft, never flashing. Under prefers-reduced-motion the animation is removed and the skeleton is a flat grey shape.

Touch

No targets.

Content

  • The busy label is "Loading" plus the thing, in the page's words: "Loading users", "Loading maintenance requests", "Loading the dashboard".
  • Never put text inside a skeleton or show "Loading…" over it; the shapes are the visual message and the label is the spoken one.

Adopted from the Shelfie design system and rewritten for the Coop admin.

Drift from the implemented admin

  • No skeletons: every admin load uses a spinner (.loading with .spin, or a per-screen spinner class). This is not a defect; the skeleton is documented as the system's option for known layouts, and the spinner page covers what the admin does today.
  • Maintenance and Messages loading: the spinner sits above the list panel, which renders empty (with its "All Requests" or conversation heading) at the same time, so the page shows two loading signals. The system uses one treatment per region.
  • Dashboard: there is no loading mock; while counts load the implemented cards are not marked busy. The system marks the metric grid aria-busy.
  • CSS gap: components.css has no circle modifier, so circles are a .skeleton sized with tokens inline.
