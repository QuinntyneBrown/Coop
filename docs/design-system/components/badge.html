Component · Status

Badge

A small pill that names a status in one or two words, so staff can scan a list and see what needs them: a maintenance request that is "New", an invitation that has "Expired", a document still in "Draft".

Overview

Use a badge to tag a row, card or table cell with its status. A badge is never clickable. If staff can press it to filter a list, it is a chip; if it explains what happened, it is an alert; a dashboard number with its own card is a metric card.

Pick the tone by what the status asks of staff, not by how important the record is:

  • Warning: someone should look at it. A maintenance request that is "New" and not yet acknowledged; a document still in "Draft".
  • Neutral (.badge--neutral, or a bare .badge): nothing to do right now. A request that is "Received", an invitation that was "Used", a user account that is "Disabled".
  • Info: work is under way. A request that is "Started".
  • Success: done or live. A request that is "Completed", a document that is "Published", a user or invitation that is "Active".
  • Danger (.badge--danger): it no longer works and needs replacing. An invitation that has "Expired".
  • Count: how many things are waiting, such as unread messages on a conversation.

The admin's maintenance statuses are New, Received, Started and Completed. The dashboard counts the first three together as "open requests", but a badge always shows the exact status, never "Open" or "In progress".

Anatomy

  1. Dot8px circle in currentColor, drawn by ::before. A second cue besides the tint; hidden on count badges.
  2. Label--text-overline: small, uppercase, wide tracking. Written in sentence case in the HTML.
  3. Pill--radius-full, 24px tall (--target-min), 8px side padding, status tint.

Sizes

One size: 24px tall. A count badge is at least 24px wide, so a single digit makes a circle.

States

Badges are not interactive, so there is no hover, focus, active or disabled state. When the status changes, the badge is replaced: "New" becomes "Received" once someone acknowledges the request. When a count reaches zero the count badge is removed, not shown as "0".

Responsive behaviour

  • Badges never wrap (white-space: nowrap) and never truncate; keep labels to one or two words.
  • In a list row or request card the badge sits at the end and the title wraps first. At 320px a row with "Kitchen tap leak" and "Completed" still fits without sideways scrolling.
  • In a table the badge stays in its cell; the table scrolls inside .table-wrap, never the page.
  • Badge text is in rem, so it grows with browser zoom and text size settings; at 400% zoom the row reflows to one column and the badge drops below the title.

Theming

Each variant reads a status pair: --color-{info,success,warning,danger}-bg for the tint and --color-{status}-fg for the label and dot. Neutral uses --color-bg-subtle and --color-fg-muted. Count uses --color-danger-solid with --color-fg-on-danger. In the dark theme the tints deepen and the labels lighten, keeping every pair above 4.5:1. Re-theme by changing the semantic status tokens, not by restyling .badge.

Accessibility

Role and pattern

A plain <span> with text and no role: the status is read as part of its row or cell. Put the badge after the title in the DOM so "Kitchen tap leak, New" reads in a sensible order. When a count changes without a page load, the page's polite live region announces it, not the badge.

Keyboard

KeyAction
TabSkips the badge. Inside a link or a focusable request card it is read as part of that control's name.

Focus

Never focusable on its own.

Labelling

The visible word is the label; colour and dot are extra cues (1.4.1), so "Expired" and "Active" never rely on red and green alone. A count badge needs context, so it carries aria-label ("2 unread messages"). The uppercase is CSS only; write the label in sentence case in the HTML so screen readers do not spell it out letter by letter.

Motion

None. A badge that changes value does not pulse, flash or bounce.

Touch

Not a target. A badge inside a request card or link adds to that target; it never needs its own.

Content

  • One or two words, in sentence case in the HTML ("Completed", "Board member"); the style uppercases it.
  • Name the state, not an instruction: "New", not "Review now".
  • Use the same word for the same state on every screen: the request is "Completed" on its card, in the dashboard list and in the filter, never "Done" in one place.
  • Counts are numerals ("2", "12"), never words.
  • Write the word, not a code: "Disabled", not "0" or "false".

Drift from the implemented admin

  • The admin uses .badge with .badge-success, .badge-warning, .badge-info, .badge-gray and .badge-danger, defined again in each feature's component styles. The system uses the BEM modifiers .badge--success, --warning, --info, --neutral and --danger from one stylesheet; .badge-gray becomes .badge--neutral.
  • Implemented badges are a plain tint in green Outfit type with no dot, so tone rests on colour alone. The system adds the dot and the violet-family look adopted for this system.
  • User accounts that are "Disabled" use .badge-danger in the Users screen. The system shows them as neutral, keeping red for things that need fixing, such as an expired invitation.
  • The Messages list shows unread messages as .unread-badge with a bare number and no accessible meaning. The system uses .badge--count with an aria-label such as "2 unread messages".
  • Some implemented labels carry stray spaces (" Active ", " Published ") from template whitespace. Badge text is the trimmed word.
  • The admin labels the last maintenance state "Completed", but its filter key is done and it also accepts "Complete" and "Done" from the API. The system shows one word, "Completed", everywhere staff can read it.
