Alert and banner

An alert is a tinted box placed right above the list or form it is about. It tells staff that something was saved ("“About us” is now on the website.") or went wrong ("We couldn't load the board list."), and it stays there until the situation changes.

Overview

The alert is how the Coop admin gives feedback. After a save, a send or a failed load, an alert appears under the page heading, above the content it is about, and stays until the page changes. The admin has no toasts: inline messages do not vanish before someone who reads slowly is done, and they sit where the person is already looking.

  • Success: the change is done and live. "“About us” is now on the website.", "Your profile is saved."
  • Danger: something failed. Say what was kept and what to do: "We couldn't load the pages. Check your connection and try again."
  • Info: neutral context that applies to the whole screen. "Changes are live as soon as you save."
  • Warning: it worked, with a catch the person should know about.

For a problem with one field, use the field's own error message (see form field). Use a dialog when the person must decide before going on. A banner (.alert.banner) is the same component across the top of every page, for news about the whole site; the admin does not use one today.

Anatomy

  1. Status icon20px, --alert-icon, aria-hidden.
  2. Title.alert__title: the message in one line.
  3. Text (optional)A plain <div>: what it means, what to do.
  4. Actions (optional).alert__actions: a link or a small button, such as Try again.
  5. Dismiss (optional).close, 24px, only for messages that are pure news. The admin's alerts have none.
  6. ContainerStatus tint, hairline border with a 4px leading edge, --radius-md, 16px padding.

Failed

A failure to load offers Try again. A failure to save says what is still true and what to do next.

We couldn't load the pages.
Check your connection and try again.
“Autumn courtyard gathering” is published, but it was not sent to members.
Press Save to try again.
That username and password don’t match
Check both and try again. Passwords are case sensitive.
Pages failed to load; a notice published but not sent (inside the document dialog); sign-in failed.

Info and warning

Available for the same placement. The admin does not show either as an alert today.

Changes are live as soon as you save
Everything on this screen is what visitors see on the public website.
This document is a draft
Members can’t see it until you publish it.
Info carries context for the whole screen; warning flags a catch. Neither is announced, because neither arrives as news.

Banner

Add .banner to drop the radius and side borders and run the alert edge to edge above main. From 640px the title, text and actions sit on one centred row. Not used in the admin today.

Sizes

One size. Alerts take the width of their container; banners take the width of the screen.

  • Shown: a success alert appears only after the server confirms the save; a danger alert appears when it does not. Never both for the same action.
  • Cleared: the alert goes when the person starts the next change, leaves the screen, or the failure is fixed (Try again succeeds). It does not time out.
  • Dismissible: optional, for pure news. Failures are never dismissible while the problem remains.

Responsive behaviour

  • Alerts are fluid; text wraps and actions wrap below the text. At 320px and at 400% zoom a long title such as "“Autumn courtyard gathering” is published, but it was not sent to members." wraps over several lines without sideways scrolling.
  • On every width the alert stays in the same place: under the page heading, above the content it is about. On phones that keeps it clear of the bottom tab bar.
  • Banners below 640px stack title, text and actions in a column; from 640px they centre on one row that wraps if needed. They push the page down and never overlap content.

Theming

Each status sets four component tokens, --alert-bg, --alert-fg, --alert-border and --alert-icon, from the semantic --color-{status}-bg/-fg/-border/-icon. Themes change the semantic tokens; in the dark theme the tints turn deep and the text light. The dismiss hover is currentColor mixed at 8%, so it follows the status.

.alert--success { --alert-bg: var(--color-success-bg); --alert-fg: var(--color-success-fg);
                  --alert-border: var(--color-success-border); --alert-icon: var(--color-success-icon); }

Accessibility

Role and pattern

WAI-ARIA alert pattern and the status role. Success uses role="status" (polite), so "“About us” is now on the website." is read after the person's current speech ends. Danger uses role="alert" (assertive). Info and warning that are part of the screen from the start take no role. Insert the alert into the page when the event happens; an alert that is in the HTML at load is read in page order, not announced.

Keyboard

KeyAction
TabReaches the action, then Dismiss if there is one, in reading order.
Enter, SpaceRuns the button (Try again), follows the link, or dismisses.

Focus

Alerts do not move focus; after a save, focus stays on the Save button or returns to the control that opened the dialog. After Try again succeeds, the alert is removed and focus moves to the first item of the loaded list. After Dismiss, focus moves to the next focusable element.

Labelling

The icon is aria-hidden; the status is said by the title in words, so it never rests on green or red alone. Dismiss is named "Dismiss". Buttons are verbs that make sense alone: "Try again".

The border is decorative; status is carried by icon, title and tint together.

Motion

None. Alerts appear in place, with no slide or fade.

Touch

Try again is a small button, 36px tall, in a full-width row. Dismiss, when present, is a 24px target pulled into the corner.

Content

  • Success names the thing and where it now is: "“About us” is now on the website.", not "Page updated successfully".
  • Failure says what happened in plain words, then what to do: "We couldn't load the board list. Check your connection and try again."
  • When something half worked, say both halves: "“Autumn courtyard gathering” is published, but it was not sent to members."
  • Never blame the person: "That username and password don’t match", not "Invalid credentials".
  • Action labels are verbs: Try again.

Drift from the implemented admin

  • The admin has two families of alert. Older screens use .alert with .alert-success or .alert-danger: green or red text in a tint, with no icon and no role. Newer screens each define their own copy, .board-alert, .pages-alert, .website-alert, .notice-alert, .page-dialog__errors and .content-dialog__errors, which do carry role="status" or role="alert" and a Material Icons glyph. The system has one .alert with BEM modifiers and inline stroke icons.
  • The .alert-success and .alert-danger messages ("Profile updated successfully", "Password updated successfully", "Theme saved successfully", "Invalid username or password", "Failed to update password", "Registration failed. Please check your invitation token.") have no live-region role, so they are not announced. The system gives success role="status" and danger role="alert".
  • The profile screens show "Profile updated successfully" even when the save fails (noted in the mock). The system shows success only after the server confirms, and a danger alert otherwise.
  • After a password change the success message appears while the reset form still shows "Current password is required" and the other required-field errors. The system clears field errors when the form resets.
  • Load failures put a .btn-secondary Try again inside the alert row. The system puts .btn.btn--sm in .alert__actions below the text.
  • Wording drifts between "… successfully" phrasing and the warmer "“About us” is now on the website." style. The system uses the second everywhere.
