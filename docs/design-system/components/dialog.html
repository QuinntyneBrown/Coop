Dialog

A focused task on top of the page: add a user, edit the website's hero, read a notice, or confirm that a page should be removed. It holds focus until it is finished or cancelled, and becomes a bottom sheet on phones.

Overview

Use a dialog for a short task that belongs to the screen underneath and must be finished or cancelled before going on. The Coop admin uses three kinds:

  • Destructive confirmation: Delete a user, Delete a document, Delete an asset, Remove a page, Remove a director. A danger icon, a question that names the thing, and a danger button whose words say what happens.
  • Form: Add a user, Edit a user, Edit a website block (the content editor), New or Edit a page (the page editor). Labelled fields, an error summary when something is missing, and Save.
  • Viewer: a document (title, text and Download) and an asset's details (a description list of file name, size and upload date, with Download and Delete).

Do not use a dialog for a message (use a toast or an alert), for navigation, or for a long form that deserves its own page. Opening a dialog from a dialog is allowed only for a confirmation, such as Delete from the asset details.

Anatomy

  1. Backdrop and frame.backdrop dims the page with --color-bg-backdrop at --z-overlay; .dialog (role="dialog", aria-modal="true") places the panel at --z-modal.
  2. Icon (destructive only).dialog__icon--danger: a 40px circle in the danger tint.
  3. Titleh2.dialog__title, the dialog's name through aria-labelledby. --text-h4 on phones, --text-h3 from 640px.
  4. CloseA ghost icon button with aria-label="Close". Same as Cancel.
  5. Body.dialog__body, usually a .stack. Its first paragraph can describe the dialog through aria-describedby. Scrolls when tall.
  6. Footer.dialog__footer: sticky, right-aligned, the safe action first and the primary or danger action last.

Variants

The examples on this page use .dialog--static, a documentation hook that draws the dialog in the page flow. They carry role="dialog" but not aria-modal, so the page stays readable; the product sets both.

Sizes

One panel width, up to 32rem. Height grows with the content up to the viewport minus --space-12; then the body scrolls and the footer stays.

  • Default: focus on the first field (forms), on Cancel (destructive) or on the title (viewers).
  • Busy: fields readonly or disabled, both footer buttons disabled, and the pressed one also aria-busy="true" with "Saving…" or "Removing…". Esc and Close do nothing until it settles.
  • Invalid: an error summary (.alert--danger.form-summary, role="alert") at the top of the body links to each field; each field gets aria-invalid="true" and a .field__error through aria-describedby. Focus moves to the summary. The dialog stays open.
  • Failed: a danger alert at the top of the body says what did not happen and that nothing typed is lost. The fields keep their values and Save can be pressed again.
  • Stacked: Delete in the asset details opens the destructive confirmation over it. Only the top dialog is active; closing it returns focus to Delete.

Responsive behaviour

  • Below 640px (--layout-breakpoint-sm) the panel is a bottom sheet: full width, pinned to the bottom, top corners --radius-xl, sliding up over --duration-slow.
  • From 640px it is centred with --space-6 around it, all corners --radius-lg, scaling in; the title grows to --text-h3.
  • The footer is sticky, so Save and Cancel stay in reach when the body scrolls or the phone keyboard is open. Buttons wrap, the main action last.
  • At 400% zoom (320 CSS px) the sheet fills the width, the long content editor scrolls inside the panel and nothing scrolls sideways.

Edit Footer

Bottom sheet at 360px: rounded top corners only, full width. Real screens get this from the base styles; no modifier is needed.

Theming

The panel is --color-bg-surface-raised with --shadow-4, over --color-bg-backdrop. In the dark theme the raised surface is lighter than the page, so the panel still lifts off a dark backdrop, and the backdrop itself is darker. The danger icon reads --color-danger-bg and --color-danger-icon. There are no dialog-specific colour tokens; re-theme through the semantic tokens.

Accessibility

Role and pattern

The WAI-ARIA APG Dialog (Modal) pattern: role="dialog", aria-modal="true", aria-labelledby pointing at the title and, when there is a description, aria-describedby. The page behind is inert while the dialog is open. In the Angular admin, open dialogs through the framework's accessible dialog primitive (such as the CDK Dialog), which provides the focus trap, Esc and focus return; these classes style what it renders.

Keyboard

KeyAction
Tab / Shift+TabMoves through the controls inside and wraps from the last to the first; focus never leaves the dialog.
EscCancels and closes, the same as Cancel or Close. Ignored while busy. In a stacked dialog it closes only the top one.
EnterSubmits a form dialog from a single-line field; activates the focused button.
SpaceActivates the focused button.

Focus

On open, focus goes to the first field (Username, Title, Page title); to Cancel in a destructive confirmation, so a stray Enter is safe; or to the title (tabindex="-1") in a viewer. On close, focus returns to the control that opened it: Add user, the row's Delete, the block's Edit. On invalid, focus moves to the error summary; on failed, the alert is announced and focus stays where it was. Keep the focused control clear of the sticky footer (WCAG 2.4.11).

Labelling

The title names the dialog and its subject: "Delete the user mira.fern?", "Edit Hero", "Courtyard plan.pdf". The close button is aria-label="Close". Every field has a visible <label for>; help and errors join through aria-describedby. The danger icon is aria-hidden; the title and the button's words carry the warning.

Motion

The backdrop fades in over --duration-base; the sheet slides up (phones) or the panel scales in from 96% (wider screens) over --duration-slow with --ease-enter. Reduced motion zeroes the durations, so it simply appears.

Touch

Footer buttons are 40px tall with 12px between them; the close button is 40px square. Both pass the 24px minimum with room to spare. The sheet keeps the actions at the bottom, within thumb reach.

Content

  • Titles say the task or the subject: "Add a user", "Edit Hero", "New page", "Autumn courtyard gathering".
  • Confirmation titles are a question that names the thing: "Remove “Our garden”?", "Delete the user mira.fern?". The body says what happens next and whether it can be undone: "It leaves the website menu straight away. You can add it again later."
  • Buttons are specific verbs and the safe one is a real choice: Cancel / Remove page, Cancel / Delete user, Cancel / Save changes. Never "OK", "Yes" or a bare "Delete" with no object in the title.
  • Busy labels say what is happening: "Saving…", "Removing…".
  • Errors say what to do ("Give the page a title") and failures say what did not happen and that nothing is lost ("Your changes weren’t saved. What you typed is still here.").

Sources

The look comes from the adopted system (first written for Shelfie); the dialogs, their copy and their states come from these admin mocks:

  • Destructive: dialogs/admin-user-delete/default, admin-document-delete/default, admin-asset-delete/default, admin-page-remove/default and busy, admin-director-remove/default and busy
  • Form: dialogs/admin-user-create/default and invalid, admin-user-edit/default, admin-content-editor/default, busy, invalid, failed, admin-page-editor/default, busy, invalid, failed
  • Viewer: dialogs/admin-document-viewer/default, admin-asset-detail/default

Drift from the implemented admin

  • Three dialog systems: the user, document, asset and document-viewer dialogs use .modal-overlay .modal-content.card .modal-actions; the website, page and board editors each have their own copy (.content-dialog, .page-dialog, .director-dialog, each with __header, __body, __footer, __errors and a -backdrop); the document delete adds .form-dialog. .modal-actions is redefined in seven component stylesheets. The system has one .dialog.
  • No dialog semantics: the .modal-overlay dialogs (Add, Edit and Delete user, Delete asset, document viewer, asset details) have no role="dialog", aria-modal or name. Only Delete document sets role="dialog" aria-modal="true" aria-labelledby.
  • Not modal: the content, page and director dialogs are native <dialog open> elements with a separate aria-hidden backdrop <div>. The open attribute shows a non-modal dialog, so the page behind is not inert and Esc does not close it. The system requires a modal dialog (aria-modal and an inert page, or the framework's dialog primitive).
  • Unnamed close buttons: the document viewer's close .icon-btn has no accessible name. The system's close button has aria-label="Close".
  • Labels: in Add and Edit user, <label>s are not joined to their fields and each field repeats the text in aria-label; the invalid state marks fields only through Angular classes, with no message. The system uses <label for>, aria-invalid, .field__error and an error summary, as the page and content editors already do.
  • Role names: the user form offers "Admin"; the roles in use are SystemAdministrator, BoardMember and Member, shown here as "System administrator", "Board member" and "Member".
  • Copy: "Confirm Delete" / "Are you sure you want to delete this document?" does not name the item. The system's confirmation title names it, as Remove “Our garden”? already does.
  • Size and look: the editors are 640px (page, director) and 720px (content) wide with a 16px radius and a raw black shadow and backdrop; the .modal-content panels are green, Outfit and 12px. The system uses one 32rem panel, --radius-lg, --shadow-4 and --color-bg-backdrop, in both themes. A wider panel for the content editor is not in the system; its two-column button fields stack instead.
  • Phones: the editors become a bottom sheet at 92vh with full-width buttons, which the system matches with .dialog's base styles; the .modal-overlay dialogs only pad above the tab bar.
  • Asset details: Download, Close and Delete sit together in one row, with the red Delete last, where the main action usually goes. Delete does open a confirmation (Confirm Delete, stacked over the details). The system keeps the confirmation and sets Delete apart on the left so the main action stays last.
