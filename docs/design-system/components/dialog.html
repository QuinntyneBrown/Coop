Dialog

A dialog interrupts the page to ask for one decision, collect a short form or show a document. It sits on a 50% black scrim, and everything behind it is unavailable until it closes.

Overview

The product has 17 dialog screens, all built from the same parts: .modal-overlay (the scrim) around .modal-content.card (the surface), with .modal-actions for the buttons. See the dialogs pattern for how dialogs are composed into flows.

  • Confirmation: a title, one sentence and Cancel / Delete (user, document and asset deletion).
  • Form: fields from form field plus Cancel / Save (create and edit user, invitation, document, maintenance request, conversation, asset upload).
  • Viewer and detail: read-only content with a close control and an action (document viewers, asset detail, maintenance detail, profile switcher).

Use a dialog only when the task cannot continue without an answer. Use an alert for information and a page for anything longer than one screen.

Anatomy

  1. Overlay (scrim).modal-overlay: fixed, fills the viewport, --color-bg-backdrop (50% black), --z-modal (1000), 16px padding so the surface never touches the screen edge.
  2. Surface.modal-content.card: white card, --radius-lg, --space-8 (32px) padding, width capped by a size class, scrolls inside when taller than 90% of the viewport.
  3. TitleAn h3 in --text-h2; it names the dialog.
  4. BodyOne sentence, a form, or document content.
  5. Actions.modal-actions: buttons on one row with --space-3 between them, each taking equal width. Cancel first, the committing action last.
  6. Close control (viewers and detail)An icon button in a .modal-header beside the title, labelled "Close".

Stacked dialog

The asset detail dialog opens a delete confirmation on top of itself. The second overlay uses the same --z-modal, so it stacks by DOM order, and its scrim darkens the first dialog. Return focus to the "Delete" button of the detail dialog when the confirmation closes. Do not open a third level.

Sizes

Size is set by a modifier on .modal-content; the surface is always width: 100% up to its cap, so it shrinks on phones.

Dialog widths
ClassMax widthTokenUse
.modal-content--layout-dialog-sm (400px)Confirmations and short forms (user, invitation, new conversation).
.modal-md--layout-dialog-md (500px)Forms with several fields (asset, maintenance request).
.modal-lg--layout-dialog-lg (700px)Document viewers and document forms.

Padding is --space-8 at every size. Height is never fixed: the surface grows with content and caps at 90% of the viewport height, then scrolls inside.

States

A dialog is shown or not shown; there is no animation in the mocks (they appear instantly). The states the product does show are the contents of the dialog:

  • Default: as in the variants above.
  • Invalid: a form dialog with aria-invalid="true" fields and an error message; see form field (admin-user-create, admin-maintenance-create, public-maintenance-create).
  • Busy: the upload dialog while a file is sending (admin-asset-upload). Buttons are disabled; see button.
  • Empty: the maintenance detail dialog when a request has no updates (public-maintenance-detail).

Busy: controls are disabled and the spinner is a status. Closing during a busy state is not offered.

Responsive behaviour

  • The overlay's 16px padding and the surface's width: 100% keep a 16px gutter on both sides at any viewport width. There is no separate phone layout (no bottom sheet): the same centred surface is used.
  • The surface caps at 90% of the viewport height and scrolls internally (overflow-y: auto). The mocks' document dialog used 80%.
  • Buttons in .modal-actions share the row equally, so they remain full-size on phones. The 32px padding is kept at 360px wide.
  • Respect device safe areas: the overlay padding must add env(safe-area-inset-*) on notched phones. This is a requirement; the mocks do not do it.

Theming

The scrim is a single token, --color-bg-backdrop.

Accessibility

Role and pattern

WAI-ARIA modal dialog pattern: the surface has role="dialog" (role="alertdialog" for destructive confirmations), aria-modal="true", and is named by aria-labelledby pointing at the title (and described by aria-describedby where there is a sentence of body). Prefer the native <dialog> element opened with showModal(), which supplies most of the behaviour below.

Requirement, not implemented in the mocks. The source dialogs are plain divs: none has a role, aria-modal, a label, a focus trap, Escape handling, or an inert page behind. The design system requires all of the following of any implementation:

Keyboard

KeyRequired behaviour
TabMoves to the next control inside the dialog; from the last control it wraps to the first (focus is trapped).
Shift+TabMoves backward; from the first control it wraps to the last.
EscCloses the dialog as Cancel. During a busy state it is ignored. A form with unsaved input keeps its data if the dialog is closed by mistake only when confirmed.
EnterIn a form field, submits the form; on a button, activates it. Never triggers a destructive action unless that button has focus.

Focus

  • On open, move focus into the dialog: to the first field in a form, to the Cancel button in a destructive confirmation (the safe choice), to the title (with tabindex="-1") in a viewer.
  • While open, the page behind is inert (or aria-hidden), cannot be scrolled and cannot be reached by Tab, pointer or screen reader.
  • On close, return focus to the control that opened the dialog; if that control was removed (for example after Delete), focus the nearest sensible heading.
  • The shared focus ring (2px --color-focus-ring) must remain visible on the surface's white background.

Labelling

The title is the accessible name; the close icon button is labelled "Close" and is the first or last control, never an unlabelled "×". A scrim click may close a viewer, but must never confirm or submit.

Motion

The mocks show no transition. If an entrance animation is added it must be a short fade, removed under prefers-reduced-motion.

Touch

Buttons in the footer are 40px tall and share the row, so each is well over 44px wide. The close icon button is 40px square.

Content

  • The title states the task: "Add user", "Confirm delete", or the document's own title in a viewer.
  • A confirmation names what will be lost. The mocks say "Are you sure you want to delete this user?"; the system prefers "Delete mira.fern? This cannot be undone."
  • Button labels are specific verbs: "Delete", "Save", "Upload". Avoid "OK" and "Yes".
  • Cancel is always present in a form or a confirmation and sits to the left of the committing action.

With a native <dialog> opened by showModal() the browser supplies the focus trap, Escape, inert page and top layer; the scrim is its ::backdrop in --color-bg-backdrop. With the mock's overlay element, the application must supply each of these itself.

Drift

  • No source dialog has role="dialog", aria-modal, an accessible name, a focus trap, Escape handling or an inert page. All are system requirements here.
  • Widths followed the screen, not the task: confirms were 400 (user), 500 (asset) and 700 (document). The system fixes confirmations at 400.
  • The public dialogs used a different surface class (.modal.card, 500px, .modal-header with an "×" close button) from the admin ones (.modal-content.card). The system has one surface and a labelled icon-button close.
  • Overlay padding was 0, 16px or 20px; the system uses 16px. Max height was 90vh or 80vh; the system uses 90vh.
  • The mock's "×" close buttons had no accessible name.
