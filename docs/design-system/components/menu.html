Menu

A menu is a short list of actions behind one button. No admin screen uses one today; it stays in the system as a core component, with a strict rule for when it may appear.

Overview

The admin mocks have no menu. The closest thing is the page actions on Pages: each page card shows "Open on the website", "Edit" and "Remove" as visible controls. Board goes further, with "Edit", "Move up", "Move down" and "Remove" on every director, and still keeps them all visible, wrapping on phones. That is the preferred approach for this audience: an action that can be seen is an action that can be found, and many staff and board members will not open a "more" button to look for one.

  • Use a menu only when an item has more actions than can stay visible even when they wrap, and none of the hidden ones is used often. Keep it to three to six items.
  • Do not use a menu for one, two or three actions; show them as buttons or icon buttons.
  • Do not use a menu to move between admin sections; that is the sidebar and the tab bar.
  • Do not use a menu to pick a value; that is a select or a radio group.

There is also no account menu. The sidebar footer shows "mira.fern" and "SystemAdministrator" as plain text, and signing out happens on Profile. The examples below use the Pages actions only to show the anatomy; they are not a proposal to hide those buttons.

Anatomy

  1. TriggerA .btn with a visible label and a chevron, aria-haspopup="menu", aria-expanded and aria-controls.
  2. Panel.menu: raised surface, hairline border, --shadow-3, --radius-md, anchored under the trigger.
  3. Item.menu__item: icon plus label, full width. A <button> for an action, an <a href> for a destination.
  4. Divider.menu__divider, aria-hidden="true"; puts the removal on its own, last.

Variants

Two triggers and one panel. The labelled trigger is preferred: it says there is something to open.

An item that removes something opens the same confirmation dialog as the visible "Remove" button would; the menu never deletes directly. There is no red danger item: the bin icon, the word "Remove" and the divider set it apart, and the red belongs on the confirmation dialog's button.

Sizes

The menu has one size: items are --control-height-sm (36px) tall and the panel is at least 12rem wide. The trigger takes any button size.

States

Hover and focus are forced with data-state; the expanded trigger uses the real aria-expanded="true".

Responsive behaviour

  • The panel is the same at every width: at least 12rem wide, anchored under its trigger and aligned to the trigger's end edge, so a trigger at the end of a card row opens inward. At 320px a 14rem panel fits with the 16px margins.
  • Script keeps the panel inside the viewport; if there is no room below the trigger it opens above. It never needs to become a bottom sheet.
  • It sits on --z-dropdown, below dialogs and toasts and above the page.
  • Item labels are two or three words and do not wrap. At 400% zoom the panel can grow to the viewport width; it never scrolls sideways.

Theming

The panel reads --color-bg-surface-raised, --color-border-default and --shadow-3; items read --color-fg-default and --color-bg-subtle for hover and focus. In dark the raised surface is lighter than the page, so elevation shows without relying on the shadow. The trigger is an ordinary button and themes as one.

Accessibility

Role and pattern

WAI-ARIA APG Menu Button pattern. The trigger is a native <button> with aria-haspopup="menu", aria-expanded and aria-controls pointing at the menu. The list is role="menu", each <li> is role="none" and each item is role="menuitem" on a native button or link. Focus inside the menu is roving: only the current item has tabindex="0".

Focus

The trigger shows the shared focus ring. Items show focus with the --color-bg-subtle fill plus the shared ring drawn inside the item (a fill alone is too faint against the raised panel), and the menu moves real DOM focus, not aria-activedescendant. A click outside closes the menu without moving focus. When a dialog opened from the menu closes, focus returns to the trigger.

Labelling

The trigger names the item it acts on: visible "Actions" plus a hidden " for About us", or aria-label="More actions for About us" on an icon trigger. The menu repeats that name with aria-label. Icons are aria-hidden; the dividers are hidden from assistive technology.

The panel border is decorative; the shadow and the raised surface set the panel apart, and its items are text.

Motion

The panel scales in from its top corner over --duration-fast with --ease-enter. Reduced motion zeroes the duration, so it simply appears.

Touch

Items are 36px tall and span the panel's full width, well over the 24px minimum. The trigger is at least a 36px small button. Hover is never needed: every item is reachable by tap and by keyboard.

Content

  • The trigger says "Actions" (or "More actions" on an icon) and names the item for assistive technology: "Actions for About us".
  • Items are verb phrases in sentence case: "Edit page", "Open on the website", "Remove page". One icon each, from the shared set.
  • Order by use, then put removal last, after a divider, so it is not hit by accident.
  • An item that opens a dialog uses the same words as the dialog's title and button.

Sources

No admin mock contains a menu. The rule on this page comes from the screens where one could have been used and was not:

  • pages/admin-pages/default (page actions: "Open on the website", "Edit", "Remove", all visible)
  • pages/admin-board/default (four visible actions per director)
  • dialogs/admin-page-remove/default (the confirmation a "Remove page" item would open)
  • pages/admin-dashboard/default (sidebar footer with name and role as plain text; no account menu)
  • pages/admin-profile/default (where signing out lives)

Drift from the implemented admin

  • No menu to correct. The admin has no .menu, dropdown or aria-haspopup anywhere, so this page records a core component for later use rather than a correction.
  • No account menu. The sidebar footer's .user-info shows "mira.fern" and "SystemAdministrator" as static text, and sign-out is a red "Logout" button on Profile. The system keeps sign-out on Profile as a secondary "Sign out" (see button) and does not add an account menu.
  • Row actions stay visible. Pages and Board already show their actions as visible buttons; the system keeps that and only changes their look (see button drift).
