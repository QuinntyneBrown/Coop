Theming

One light appearance, three token tiers, and component tokens as the override points. No dark theme is implemented or specified.

Overview

The implemented Coop product ships one light appearance. There is no dark palette, no theme switch and no per-user colour mode; the mocks README records that ?theme=dark keeps the same light product. No dark theme is specified by this design system either. tokens.css declares color-scheme: light, and the documentation pages have no theme toggle.

Theming here therefore means how tokens are layered, so that a value can change in one place, and how a component can be adjusted without editing its stylesheet. It does not mean theme variants.

The three tiers

Tokens come in three tiers. Each tier references the one below it, never the reverse.

  1. Primitives (--palette-*, --font-*) are raw values: a hex colour, a font stack, a size. Components never use them directly. This is the only tier where raw colour values live.
  2. Semantic tokens (--color-*, --text-*, --space-*, --radius-*, --shadow-*, --duration-*, --z-*, --layout-*) name a role and alias a primitive. Components and pages consume these. Example: --color-accent aliases --palette-green-700.
  3. Component tokens (--button-bg, --button-height, --icon-size, --alert-bg, --field-border, --avatar-size, --icon-btn-size) are declared inside a component rule in components.css and always alias a semantic token. They are the supported override points.

The system also honours three user preferences by overriding semantic tokens in tokens.css: prefers-reduced-motion (shortens durations), prefers-contrast: more (stronger borders and secondary text) and forced-colors (system colours for the focus ring and borders). These are accessibility adaptations of the single appearance, not themes.

Component overrides

A component reads its look from its own tokens. To change one instance, set the component token on that element or a wrapper; to change a role everywhere, change the semantic token. .btn-primary works exactly this way: it only reassigns the button tokens.

Show the override
.btn-danger {
  --button-bg: var(--color-danger-solid);
  --button-bg-hover: var(--color-danger-solid-hover);
  --button-fg: var(--color-fg-on-danger);
  --button-border: var(--color-danger-solid);
}
Variants are token reassignments, not new rules. See Button.

Overrides must point at semantic tokens (var(--color-accent)), never at a literal colour, so contrast is checked once in tokens/contrast-pairs.json.

tokens.json

tokens/tokens.json is the same set of tokens in the Design Tokens Community Group format. It is exported from tokens.css, which stays the source of truth. Each entry has $type, $value and the CSS custom property name under $extensions["com.agent-toolkit"].css.

{
  "layout": {
    "breakpoint": {
      "sm": {
        "$type": "dimension",
        "$value": "40rem",
        "$extensions": { "com.agent-toolkit": { "css": "--layout-breakpoint-sm" } }
      }
    }
  }
}
  • Web code consumes tokens.css directly through var(--token). Link it before components.css.
  • Other tools (design software, native code, style generators) read tokens.json and use the css extension to map back to the property name.
  • Edit tokens.css first, then regenerate tokens.json. Do not edit both by hand.

Usage

  • Add a new value as a primitive first, then alias it with a semantic token. Pages and components use the semantic name.
  • Do not add a dark or high-contrast theme. Preference media queries may adapt existing tokens; they do not introduce a second palette.
  • Do not use data-theme to switch appearance. The mocks set data-theme="light" only as a constant.
  • When a component needs a new adjustable value, declare it as a component token that aliases a semantic token.
