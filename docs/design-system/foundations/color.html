Foundation · Color

Color

Calm grey surfaces, one violet accent for the next thing to do and four status hues, in a light and a dark theme that both pass WCAG 2.2 AA.

Overview

The Coop admin is where co-op staff and board members of OWN Housing Co-op handle maintenance requests, documents, messages and members. Its colour is quiet on purpose: grey surfaces, one violet accent that marks the next thing to do (“New request”, “Add user”, “Save theme”), and four status hues that say what state a record is in. The palette is adopted unchanged from the Shelfie design system.

Colour lives in two tiers. Primitives (--palette-*) are raw ramps that nothing reads directly. Semantic tokens (--color-*) name a job (“text on a card”, “edge of a form field”) and are what components use. A theme swaps the semantic tokens and leaves the primitives alone.

  • Use the semantic token that names the job, never a palette step.
  • Pair every foreground with the background it was checked against in contrast pairs.
  • Status is never colour alone: every badge has a word, and every alert, toast and field error has an icon and words.

Primitive ramps

Violet: the accent

Primary buttons, links, the current sidebar item, the selected tab, the checked checkbox and the focus ring. Step 600 is the light-theme accent; 300 takes over in the dark theme.

Gray: neutrals

Text, surfaces and borders. Steps 150, 350, 450, 475, 750 and 925 exist so the dark theme reads its text, edges and wells from the ramp instead of raw values.

Blue: information

Only for information: the “You have 2 unread messages” notice and the Started badge on a maintenance request. Never for actions.

Green: success

Completed requests, Published documents, Active users and invitations, and the “saved” messages after a change.

Amber: warning

New maintenance requests that nobody has picked up yet, and Draft documents that members cannot see.

Red: danger

Errors, invalid fields, the unread count badge, Expired invitations and the Delete button inside a “Confirm delete” dialog.

Base

--palette-white and --palette-black are the two ends. Only the light surfaces, the label on the accent and the dark-theme backdrop read them, through semantic tokens.

Contrast pairs

Every pair in tokens/contrast-pairs.json (69 distinct pairs; a few are listed twice in the file for different components and appear once here with both notes), measured live in both themes. 4.5:1 is the minimum for text (WCAG 1.4.3); 3:1 for control edges, meaningful icons and the focus ring (1.4.11, 2.4.11). The one pair with a 1:1 minimum is a decorative alert border, listed so nobody mistakes it for a control edge.

Usage

Rules

  • One accent per view. The violet fill marks the next step on the screen: “New request” on Maintenance, “Add user” on Users, “Save theme” in Settings. Everything else is a secondary or ghost button.
  • Text tokens follow the surface. Muted text on a subtle chip is checked; muted text on the accent fill is not. If a pair is not in the list, add it to contrast-pairs.json and run the checker before shipping.
  • Danger is for loss. The red fill appears on the confirming button of a destructive dialog (“Delete” in “Confirm delete”, removing a director) and on the count badge, nowhere else.
  • Blue is information, not action. Links and buttons are violet.
  • Status describes state, not importance. A New request is amber because nobody has picked it up, not because it is urgent; priority is written as a word.
  • No raw values. No hex values, colour functions or colour names in components or pages; check_design_system.py fails the build on them.

Adding a theme

A theme is a block of semantic overrides. Pick existing palette steps (or add a ramp under Primitives), override only --color-* tokens, set color-scheme, then run the contrast checker for every pair. Components need no change.

[data-theme="example"] {
  --color-accent: var(--palette-blue-700);
  --color-accent-hover: var(--palette-blue-800);
  --color-accent-active: var(--palette-blue-900);
  --color-accent-subtle: var(--palette-blue-50);
  --color-accent-subtle-hover: var(--palette-blue-100);
  --color-fg-accent: var(--palette-blue-700);
  --color-focus-ring: var(--palette-blue-700);
  color-scheme: light;
}

See Theming for where the block goes and how to test it.

Accessibility

  • Text reaches 4.5:1 on every surface it sits on, in both themes. Many of the people using the admin are older and read on laptops and phones in daylight; muted text is still a solid grey that passes, never a transparent tint of the body colour.
  • Controls and icons that carry meaning reach 3:1: field edges (--color-border-strong), the focus ring, the checked checkbox, the selected tab indicator, progress fills against their track and the toast status icons.
  • Decorative edges (--color-border-default) are exempt and say so; the control they belong to is identified another way.
  • Use of colour (1.4.1): links in running text are underlined, status badges always carry their word (“New”, “Completed”), the current sidebar item has a tinted background and aria-current="page", and errors have an icon and words.
  • Preferences: under prefers-contrast: more decorative borders become strong and muted text becomes default; under forced-colors: active the focus ring becomes Highlight and borders CanvasText.

Drift from the implemented admin

The mocks are captures of the running Angular admin, which does not use this system yet. Each difference below is drift: the system value is the one to build to.

  • Accent. The admin’s accent is green (#3d8a5a, hover #2d6b44) on .btn-primary, links and the active sidebar item. White on that green measures 4.2:1, under the 4.5:1 text minimum. The system uses violet 600 with --color-fg-on-accent, which passes in both themes.
  • Current sidebar item. .sidebar-nav .nav-item.active is a solid green fill with white text (4.2:1). The system uses .nav-link[aria-current="page"] with --color-accent-subtle and --color-fg-accent.
  • Status badges. .badge-success, .badge-warning, .badge-info and .badge-danger are 10% tints with mid-tone text: about 3.4, 3.0, 3.3 and 3.9:1. The system’s .badge--success, --warning, --info, --danger and --neutral use checked *-fg on *-bg pairs (4.5:1 or more). .badge-gray becomes .badge--neutral.
  • Edges. Cards, dividers and form fields share one light grey edge (#e5e4e1, 1.3:1 on white), so fields fail WCAG 1.4.11. The system splits decorative --color-border-default from control --color-border-strong.
  • Secondary text. The admin sets secondary text as an 80% transparent version of the body colour. The system uses opaque greys (--color-fg-muted, --color-fg-subtle) so contrast is the same on every surface.
  • Metric icons. Each dashboard .metric-icon has its own hand-mixed tint, including a purple for Documents that belongs to no palette. The system uses .metric-card__icon (accent) and its --warning, --success and --info variants.
  • Canvas and danger. The admin canvas is a warm off-white (#f5f4f1) and danger red is #dc3545 (4.5:1, just passing). The system uses cool gray 50 and red 600/700.
  • Focus. Fields replace the outline with a faint 3px green halo at 10% opacity, which is close to invisible. The system draws a solid 2px --color-focus-ring at 3:1 or more.
  • Themes. The admin is light only and ignores prefers-color-scheme. The system has a light and a dark theme, both checked.
  • Theme customisation. Settings › Theme lets an administrator type any primary, background, accent and text colour, and nothing checks the result for contrast. In this system colours are fixed tokens; a custom theme is a block of semantic overrides that must pass check_contrast.py.
  • Logo. The co-op logo in the sidebar uses its own terracotta, peach and amber fills, outside any palette. This documentation draws the mark with token fills; the real logo artwork is a brand asset outside this system.
