Foundation · Layout

Layout

The admin shell: a sidebar beside the content from 768px and a bottom tab bar below it, on a mobile-first grid of 4, 8 and 12 columns.

Overview

The admin is mobile first. Base styles target a 360px phone, where the admin’s navigation is a bottom tab bar. From 768px the sidebar (256px) sits beside the content and the tab bar goes away. Two breakpoints (768px and 1024px) add columns, wider gutters and wider margins by changing three tokens, so components rarely need their own media queries.

  • Wrap every signed-in screen in .app-shell: the sidebar, then .app-shell__main, then the tab bar.
  • Lay content out on .container + .grid; the grid reads --layout-columns, --layout-gutter and --layout-margin.
  • Use min-width queries in rem only.
  • No screen scrolls sideways at 320px, which is what a laptop shows at 400% zoom.

--layout-breakpoint-lg1024px · 64remLaptops12 columns, 32px gutter, 48px margin; .span-4/5/7/8 split

Custom properties cannot be read inside @media, so the breakpoint tokens are documentation and JavaScript values; CSS repeats the rem number by convention (@media (min-width: 48rem)). Because the queries are in rem, a person who sets a larger default font size reaches the phone layout sooner, which is what they need.

Admin shell

Every signed-in admin screen shares one shell. The sign-in, registration and password screens use the auth template instead and show no navigation.

The sidebar: the co-op’s mark and name, thirteen sections in the order the admin uses, and the signed-in person with their role. The current section has the subtle accent tint and aria-current="page".
  • .app-shell becomes a two-column grid from 768px: --layout-sidebar-width (256px) and the rest for .app-shell__main.
  • The sidebar is sticky and full height (100dvh). When the thirteen links do not fit, for example at 200% zoom on a laptop, the sidebar scrolls on its own and the page does not move.
  • .app-shell__main has min-width: 0 so wide tables scroll inside their .table-wrap instead of pushing the page sideways.

Bottom tab bar, below 768px

DashboardRequestsDocumentsMessages
Below 768px the sidebar is hidden and the tab bar (64px, --layout-tabbar-height) carries four destinations (Dashboard, Requests, Documents, Messages) and a More button that opens every section in a dialog.
  • The tab bar is fixed to the bottom, adds env(safe-area-inset-bottom), and the shell’s .has-tabbar pads the page bottom so nothing sits under it.
  • Each tab is at least 44px tall (--target-comfortable) and keeps a visible label under its icon.
  • Every section on phones: the tab bar holds four of the thirteen sidebar sections. Its fifth item, More, is a button (aria-haspopup="dialog") that opens a dialog listing all thirteen with .sidebar__nav, the current one marked, and My profile at the end; see the tab bar. The implemented admin instead stacks the whole sidebar above the content on phones.
  • The admin has no top bar. --layout-topbar-height sizes the top bar component, which the admin shell does not use.

Columns, gutters and margins

The live grid below uses the real tokens: resize the window to watch it go from 4 to 8 to 12 columns. In the admin the grid lives inside .app-shell__main, so from 768px it spans the width beside the sidebar, not the whole window.

  • .grid is repeat(var(--layout-columns), minmax(0, 1fr)) with gap: var(--layout-gutter).
  • .span-4, .span-5, .span-7, .span-8 are full width until 1024px, then take that many of 12 columns: 8 + 4 for a main column with an aside, 7 + 5 for two columns of similar weight.
  • .grid--auto fills cards at a minimum of 18rem each; .metric-grid fills the dashboard’s metric cards at a minimum of 14rem, so four counts sit in one row on a laptop and one per row on a phone.

Container and measure

  • .container is full width, capped at --layout-container-max (1280px), centred, with --layout-margin on both sides.
  • Prose stops at --layout-measure (65ch); every <p> has it as a max-width, so a long notice or bylaw stays comfortable to read on a wide screen.
  • The auth card is 26rem wide and centred in the viewport (.auth-layout, .auth-card); a dialog panel is 32rem.

Usage

  • Put spans on grid items with the .span-* classes; never write style="grid-column: span 8" with a max-width override.
  • A page has one .container inside .app-shell__main.
  • Use 100dvh, not 100vh, for full-height layouts so mobile browser bars do not clip content.
  • Never hide content at a breakpoint unless it is reachable another way; see the open question about the nine sections that are not in the tab bar.

Accessibility

  • Reflow (1.4.10): every screen works at 320 CSS px wide (400% zoom) in one column with no sideways scroll; only data tables scroll, inside .table-wrap.
  • Focus not obscured (2.4.11): the fixed tab bar must never hide the focused element; .has-tabbar pads the page bottom by the tab bar’s height so the last field and button can scroll clear of it.
  • Order (2.4.3): visual order equals DOM order at every width: sidebar, main, then tab bar.
  • Landmarks: one main per screen; the sidebar navigation is a nav labelled “Admin” and the tab bar a nav labelled “Admin, phone”, so both can be told apart. A skip link jumps past the thirteen sidebar links.
  • Consistent navigation (3.2.3): the sidebar lists the same sections in the same order on every screen.

Drift from the implemented admin

The mocks are captures of the running Angular admin, which does not use this system yet. Each difference below is drift: the system value is the one to build to.

  • Sidebar width. The implemented .sidebar is 260px, position: fixed, and .layout-main is pushed over with a 260px left margin. The system’s sidebar is 256px (--layout-sidebar-width) in a CSS grid, so nothing depends on a matching margin.
  • Phones. Below 768px the implemented sidebar becomes static and stacks all thirteen links above the page, while .bottom-tab-bar also shows. The system hides the sidebar below 768px and uses the tab bar alone; reaching the other nine sections on phones is an open question.
  • Breakpoint edge. The admin uses max-width: 768px and min-width: 769px in pixels, so at exactly 768px it shows the phone layout. The system uses min-width: 48rem, so 768px gets the sidebar, and the breakpoint moves with the font size.
  • Tab bar on sign-in. The sign-in page shows the bottom tab bar to people who are not signed in. The system’s auth template has no navigation.
  • Content width. The dashboard caps its content at 800px and pads it 24 × 20px; other screens cap at 900px or 1200px with their own padding. The system uses .container and --layout-margin everywhere.
  • Full height. The admin uses 100vh, which mobile browser bars can clip. The system uses 100dvh.
  • Labels. The sidebar and tab bar labels are kept as the admin has them; the content foundation’s sentence-case rule applies when they are next edited (for example “Roles & privileges”).
