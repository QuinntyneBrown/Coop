Overview and voice

This page describes the voice the mocks already have, taken from the real copy in docs/mocks. It records patterns, and where two mocks say the same thing differently it names the inconsistency and gives a clearly marked Recommended wording. The product's reference date is 13 October 2026 and all names and addresses are fictional.

The voice is plain, short and friendly: a neighbourhood cooperative, not a bank. Copy addresses the member as "you" ("Your" in onboarding headings), uses contractions ("Here's your overview", "You're all set!", "we'll send you a link") and avoids jargon and exclamation marks except to welcome or confirm completion.

Casing and button verbs

Casing

  • Buttons and links that act: Title Case. "Save Changes", "Create Account", "Update Password", "Send Reset Link", "Go to Dashboard", "Add User", "Edit Profile". Short words such as "to" stay lower case.
  • Screen and dialog titles: Title Case. "Maintenance Requests", "Change Password", "Edit Member Profile", "Asset Details", "Confirm Delete".
  • Labels: Title Case. "First Name", "Confirm New Password", "Invitation Token", "Board Title". Optional fields add "(optional)".
  • Sentences (subtitles, hints, errors, empty states, success): sentence case, ending with a full stop only when there is more than one sentence or the line is a full sentence ("No public notices at this time.").
  • Placeholders: sentence case, an example or instruction: "Enter your username", "Brief title for your request", "Search documents...".
  • Status and category values (New, Received, Started, Completed, Draft, Published, Active, Expired, Used, Low, Medium, High) are single Title Case words in badges.

Auth headings are the exception: they use sentence case ("Welcome back", "Join your cooperative", "Set up your profile") while the admin onboarding headings use Title Case ("Select Your Unit").

Button verbs

  • Create something: Create for records ("Create Account", "Create Invitation", "Create Request"), Add for list members ("Add User", "Add Privilege"), New for the entry button ("New Request", "New Document", "New Conversation").
  • Change something: Save Changes for profile edits, Update Password for passwords, Edit / Edit Profile to start editing.
  • Leave or dismiss: Cancel when a flow was started, Close for viewers, Done after success, Skip and Back in onboarding.
  • Destructive: Delete in a "Confirm Delete" dialog; the dialog states the object ("Are you sure you want to delete this user?").
  • Session: Sign In, Create Account, Log Out.
  • Busy: the button label becomes the present participle with three dots ("Signing in...", "Creating account...").

Message formulas, dates

Formulas

  • Required field error: "Field is required" ("Username is required", "First name is required"). Choice: "You must accept the terms".
  • Mismatch error: "Passwords do not match".
  • Form-level failure: "What failed. What to check." ("Registration failed. Please check your invitation token.", "Failed to change password. Check your current password."). A short fact is allowed when nothing can be fixed ("Invalid username or password").
  • Empty state: "No things found" for lists, "No things yet" for things the person creates, "No recent things" on dashboards. They sit under a 48px icon and, where the user can act, next to the entry button. The mocks reuse the empty-state text for no-results; no separate "no matches" wording exists.
  • Success: "Thing updated successfully" ("Profile updated successfully", "Password updated successfully", "Theme saved successfully").
  • Hints: one sentence of instruction or a rule ("Password must be at least 8 characters long").
  • Greeting: "Hello, FirstName" followed by "Here's your overview".

Dates and numbers

  • Dates: short month, day and year in US order: Oct 13, 2026. With a time: Oct 13, 2026, 8:00 AM (12-hour with AM/PM). Form date fields hold ISO values (2026-10-13).
  • The asset detail dialog shows seconds ("Oct 13, 2026, 8:00:00 AM") and a raw byte count ("2048"). These are unformatted values rather than a chosen style.
  • Counts are bare numbers beside a label ("Requests 4").

Usage

  • Use the verb table above before inventing a new label. A button names what it does to the object ("Create Request"), not "Submit" or "OK".
  • Write error text that says what is wrong and how to fix it, next to the field, and in a form that screen readers announce (see Accessibility).
  • Use "Oct 13, 2026" style dates everywhere, and drop seconds.
  • Use the three-dots busy text while a form submits and keep the button label stable in width where possible.
  • Keep copy fictional-safe: invented names, the address 101 Fictional Court, and .invalid e-mail domains in examples.

Drift

  • Heading and button casing differs between the public and admin apps for the same screens.
  • Equivalent actions have different labels (Submit, Submit Request, Create Request; Logout, Log Out).
  • The two validation messages for terms and for password mismatch differ between apps.
  • Busy labels use three ASCII dots and differ in wording ("Creating..." versus "Creating account...").
  • Asset detail shows raw bytes and seconds in the timestamp.
